# Qwen3.8-27B × Databricks AI Gateway — 성능 측정 결과

**측정 대상**: `Qwen/Qwen3.8-27B` 사전양자화 FP8 · vLLM 0.28.0 · A100 80GB × 1 · Azure Databricks  
**측정 일시**: 2026-09-09 05:57 ~ 07:33 UTC  
**유효 요청**: **1,553건** (전체 1,686건 중 무효 133건 배제 — [부록 B1](appendix/B1_method_and_environment.md))  
**측정 범위**: AI Agent 워크로드 — 체감 지연 · 추론 예산 · 도구 호출 · 멀티턴 · 장문 RAG · 처리량 · 실패 모드  
**게이트웨이 비교**: driver-proxy 직접 경로와 **교대 발사 쌍 비교**로 게이트웨이 계층 비용을 분리 측정

이 보고서는 **배포 가이드와 독립**입니다. 배포 절차는 [배포 가이드](../deployment/README.md)를 보십시오.

## 1. 한 장 요약

### 1.1 이 구성이 감당하는 것

| 항목 | 실측값 | 조건 |
|---|---|---|
| 처리량 (권장 운영점) | **3.274 req/s = 196.4 req/분** | 동시성 32 · 출력 256토큰 고정 |
| 출력 토큰 처리량 | **838.0 출력토큰/초** | 동시성 32 · 출력 256토큰 고정 |
| 백만 출력토큰당 비용 | **1.64 USD** | 동시성 32 · 출력 256토큰 · 4.959 USD/시간 기준 |
| 본문 첫 글자까지 (체감 지연) | p50 **3.549초** · p95 7.145초 | 짧은 질문 · 스트리밍 |
| 토큰 간 간격 | p50 **21.4 ms** (n=2,299) | 프롬프트 34배에도 불변 |
| 컨텍스트 상한 | **131,072 − `max_tokens`** | 초과 시 400 즉시 |
| 게이트웨이 추가 비용 | 요청당 **+0.05초** (p95 +0.22초) · 처리량 손실 **없음** | 출력 200토큰 고정 · 12쌍 전부 양수 |

### 1.2 AI Gateway 를 붙이는 판단

**게이트웨이 경유 비용은 요청당 약 +0.05초(상대값 1.2 %)이고 처리량은 깎이지 않습니다**
(부하 중 −0.5 %, 측정 오차 범위). 대가로 중앙 집중 인증 · rate limit · 사용량 추적 ·
`cluster_id` 를 노출하지 않는 안정적 URL 을 얻습니다. **성능을 이유로 게이트웨이를 피할 근거는
이 측정에서 나오지 않았습니다.**

단, 게이트웨이는 **기본 rate limit 120 calls/분**을 함께 가져옵니다. 이 값은 이 GPU 의 포화
처리량 **196.4 req/분보다 작으므로**, 짧은 응답 워크로드에서는 GPU 가 아니라 **한도가 먼저**
걸립니다. → [P1 직접 대 게이트웨이](P1_direct_vs_gateway.md) · [P3 용량과 비용](P3_capacity_and_cost.md)

### 1.3 반드시 알아야 할 위험 세 가지

> **① 추론 폭주 — HTTP 200 인데 본문이 비어 있습니다.**  
> 이 모델은 추론 모델이고 추론 토큰이 `max_tokens` 예산을 **먼저** 소비합니다. 어려운 추론 질문은
> 예산 전량을 추론에 쓰고 **본문 0자**로 끝났습니다(같은 질문 7건 중 6건). `max_tokens=6000` 에서는
> **130.3초를 쓰고 본문 0자**였습니다. 지연이 예산에 선형(약 46 tok/s)이므로 **예산을 키우면 실패까지
> 걸리는 시간만 늘어납니다.** 오류가 아니라 200 이 돌아오므로 클라이언트가 감지해야 합니다.  
> **유일하게 신뢰할 수 있는 감지 조건은 `finish_reason == "length"` 입니다.**  
> → [P2 Agent 워크로드](P2_agent_workload.md)

> **② TTFT 를 응답 시간 SLA 로 쓰면 안 됩니다.**  
> 첫 SSE chunk 는 p50 **0.271초**에 오지만 그것은 **추론의 시작**입니다. 사용자가 읽을 수 있는
> 본문 첫 글자는 p50 **3.549초** · p95 **7.145초**이고, 4K 프롬프트 요약에서는 **15.622초**입니다.
> 두 값의 차이가 13배이므로 어느 쪽을 SLA 로 쓰는지가 설계를 바꿉니다.  
> → [P2 §체감 지연](P2_agent_workload.md)

> **③ 도구 호출을 강제할 수 없고, `"required"` 는 `finish_reason` 까지 오염시킵니다.**  
> `tool_choice` 로 특정 함수를 지정하는 것과 `"required"` 는 **조용히 무시**되고 `auto` 처럼
> 동작합니다(HTTP 200 · `tool_calls=None`). 게이트웨이 경유와 driver-proxy 직접에서 **동일**하므로
> 게이트웨이를 우회해도 해결되지 않습니다. `"none"` 은 정상 작동합니다.  
> **더 위험한 것**: `tool_choice: "required"` 는 `tool_calls` 가 `None` 인데
> **`finish_reason` 을 `"tool_calls"` 로 반환합니다**(10/10). `finish_reason` 으로 도구 호출 여부를
> 판정하는 코드는 여기서 깨집니다 — **`message.tool_calls` 를 직접 확인**하십시오.  
> 구조화 추출이 목적이라면 `response_format` 을 쓰십시오(18/18 성공).  
> → [P1 §tool_choice](P1_direct_vs_gateway.md) · [P2 §도구 호출](P2_agent_workload.md)

## 3. 측정 대상 구성

```
외부 클라이언트
  → https://<workspace>/serving-endpoints/qwen38-27b-vllm/invocations       [AI Gateway]
  → https://<workspace>/driver-proxy-api/o/<ws_id>/<cluster_id>/8005/v1/... [driver-proxy]
  → vLLM 0.28.0 (클러스터 드라이버 프로세스 · 포트 8005)
```

**두 경로를 모두 측정**했습니다. 게이트웨이 경유와 driver-proxy 직접을 교대로 발사해 쌍별 차이를
냈고, 그 차이가 **AI Gateway 계층이 추가하는 비용**입니다. 「직접」 경로도 Databricks driver-proxy 를
지나므로 이 값은 **vLLM 순수 성능과의 차이가 아닙니다** — 이 구분은
[P1 §비교의 전제](P1_direct_vs_gateway.md)에서 다룹니다.

**서버 구성** (실측 cmdline):

```
vllm serve /local_disk0/models/Qwen3.8-27B-FP8 --served-model-name qwen38-27b \
  --host 0.0.0.0 --port 8005 --max-model-len 131072 --gpu-memory-utilization 0.90 \
  --max-num-seqs 32 --max-num-batched-tokens 7840 --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml --language-model-only \
  --kv-cache-dtype fp8
```

**노드**: `Standard_NC24ads_A100_v4` (A100 80GB × 1) · DBR 19.5 GPU ML · driver 580.159.03  
**모델**: 약 30 GB · safetensors 66개 · 하이브리드 어텐션 64층  
**게이트웨이**: external model `provider: custom` · rate limit 120 calls/분 · usage tracking on

배포 절차와 각 플래그의 근거는 [배포 가이드 STEP3](../deployment/STEP3_vllm_serve.md)에 있습니다.

### 4.4 처리량 · 용량

| 동시성 | 처리량 | p50 | p95 |
|---|---|---|---|
| 1 | 0.162 req/s | 6.142초 | 6.224초 |
| 32 (**권장 운영점**) | **3.274 req/s** | 9.646초 | 9.671초 |
| 48 | 3.457 req/s (**+5.6 % 뿐**) | 9.862초 | 18.880초 (**2배**) |

N=32 의 **p99 는 18.850초**입니다(유효 표본 94건 중 상위 1 % = 관측 1건). p95 를 SLA 로 쓰면
9.671초지만 p99 를 약속해야 한다면 동시성을 32 보다 낮추십시오 — N=24 는 p95 8.888초 · p99 8.910초로
꼬리가 갈라지지 않습니다.

**병목은 KV 캐시가 아니라 배치 슬롯입니다**: `num_requests_running` 최대 32.0(= `--max-num-seqs`),
`waiting` 최대 16.0, **KV 사용률 최대 15.041 %**, preemption 0.
배치를 채우면 N=1 대비 처리량 **20.2배** · 지연은 1.57배입니다.
**N=48 은 포화가 아닙니다** — 처리량이 +5.6 % 더 늘지만 p95 가 2배가 되므로 권장하지 않습니다.

## 5. 이 숫자를 신뢰할 수 있는 범위

**신뢰할 수 있는 것**

- 모든 요청이 타임스탬프와 함께 append-only JSONL 로 남아 있고 집계를 재현할 수 있습니다
  ([부록 B4](appendix/B4_evidence_index.md))
- 게이트웨이 오버헤드는 **출력 길이를 고정해** 측정했습니다. 고정하지 않으면 차이의 부호가
  뒤집혀 측정이 성립하지 않습니다([P1 §측정 방법](P1_direct_vs_gateway.md))
- 부하 시험 중 `/metrics` 를 함께 기록해 **외부 트래픽 혼입이 없었음**을 확인했습니다
  (`num_requests_running` 최댓값이 정확히 `--max-num-seqs` 값인 32.0)
- 스트리밍은 게이트웨이에서 **버퍼링되지 않습니다.** chunk 가 토큰 단위로 도착합니다
  (게이트웨이 6건 중 4건은 chunk 수와 `completion_tokens` 가 정확히 일치, 2건은 1~3토큰 차이 ·
  직접 경로는 6/6 정확히 일치)
- 측정 중 서버가 한 번 재기동되었고, 그 구간의 **133건을 시각 기준으로 배제**했습니다

**신뢰 범위 밖**

- **단일 리전 · 단일 노드 · 단일 시점**입니다 (Azure koreacentral · A100 80GB × 1 · 약 2시간)
- 여러 항목의 **표본이 작습니다** (n=2~12). `tool_choice` 조건별 n=3~5 · 멀티턴 n=5세션 ·
  장문 각 구간 n=2 · prefix 캐시 콜드 기준선 **n=1**
- **GPU 여러 장으로의 확장 선형성은 측정하지 않았습니다.** 용량 산정식은 1장 실측을 나눈 것입니다
- 비용 수치는 **출력 256토큰 고정 조건**입니다. 출력 길이별 일반화는 하지 않았습니다
- 장문 정확성 18/18 은 **천장효과**이며 고객 데이터로 별도 평가가 필요합니다

측정하지 않은 항목의 전체 목록은 [부록 B5](appendix/B5_limitations.md)에 있습니다.
**고객 환경에서 재측정을 권장하는 항목**도 같은 부록에 정리했습니다.
