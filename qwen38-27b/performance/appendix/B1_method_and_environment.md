# 부록 B1 · 측정 방법과 환경

**이 부록이 답하는 질문**: "이 숫자들을 어떻게 측정했고, 왜 믿을 수 있는가?"

성능 수치는 측정 방법에 따라 크게 달라집니다. 이 부록은 각 수치가 **어떤 조건에서 나왔는지**와
**측정을 무효로 만들 수 있었던 요인들을 어떻게 통제했는지**를 기록합니다. 고객 환경에서
같은 측정을 재현하려면 이 부록의 조건을 맞추셔야 합니다.

---

## 1. 환경

| 항목 | 값 |
|---|---|
| 클라우드 · 리전 | Azure · koreacentral |
| 노드 | `Standard_NC24ads_A100_v4` — A100 80GB × **1장** |
| 런타임 | DBR 19.5 GPU ML · NVIDIA driver 580.159.03 |
| 추론 서버 | vLLM **0.28.0** · torch 2.13.0+cu130 (격리 venv) |
| 모델 | `Qwen/Qwen3.8-27B` 사전양자화 FP8 · 약 30 GB · safetensors 66개 · 하이브리드 어텐션 64층 |
| 엔드포인트 | AI Gateway external model · `provider: custom` · rate limit 120 calls/분 · usage tracking on |
| 클라이언트 위치 | 워크스페이스 외부 (로컬 PC) — 즉 **네트워크 왕복이 포함된 값**입니다 |
| 측정 시각 | 2026-09-09 05:57 ~ 07:33 UTC (약 1시간 36분) |

**서버 구성** (실측 cmdline):

```
vllm serve /local_disk0/models/Qwen3.8-27B-FP8 --served-model-name qwen38-27b \
  --host 0.0.0.0 --port 8005 --max-model-len 131072 --gpu-memory-utilization 0.90 \
  --max-num-seqs 32 --max-num-batched-tokens 7840 --reasoning-parser qwen3 \
  --enable-auto-tool-choice --tool-call-parser qwen3_xml --language-model-only \
  --kv-cache-dtype fp8
```

### 1.1 기동마다 동일했던 지표 — 정상 판정에 쓸 수 있습니다

고객 환경에서 이 4개가 일치하면 서버가 같은 구성으로 떴다고 판단할 수 있습니다.

| 항목 | 값 |
|---|---|
| FP8 커널 | `MarlinFP8ScaledMMLinearKernel` |
| attention 백엔드 | `FLASHINFER` |
| attention block size | 1568 |
| mamba page padding | 0.13 % |

### 1.2 기동마다 달라지는 지표 — 정상 판정에 쓰면 안 됩니다

**같은 플래그인데 KV 캐시 용량이 달라집니다.** 기동 시점의 여유 VRAM 에 따라 결정되기 때문입니다.

| 측정 구간 | KV 캐시 | 최대 동시성 (131K/요청) | Available KV |
|---|---|---|---|
| A | 1,188,386 토큰 | 9.07x | 39.06 GiB |
| B | 1,240,814 토큰 | 9.47x | 40.78 GiB |

차이 약 **4.4 %** 입니다. **정확값 일치로 정상/이상을 판정하면 안 되고**, 용량에 의존하는 지표를
두 구간에 걸쳐 합산해서도 안 됩니다. 이 보고서는 그런 합산을 하지 않았습니다.

## 2. 경로 — 무엇과 무엇을 비교했는가

```
[게이트웨이 경유]
  클라이언트 → https://<ws>/serving-endpoints/qwen38-27b-vllm/invocations
             → https://<ws>/driver-proxy-api/o/<ws_id>/<cluster_id>/8005/v1/...
             → vLLM:8005

[직접]
  클라이언트 → https://<ws>/driver-proxy-api/o/<ws_id>/<cluster_id>/8005/v1/...
             → vLLM:8005
```

**「직접」 경로도 Databricks driver-proxy 를 지납니다.** 따라서 두 경로의 차이는
**AI Gateway 계층만의 추가 비용**이며, vLLM 프로세스에 로컬로 붙은 값과의 차이가 아닙니다.
이 구분을 흐리면 게이트웨이 오버헤드를 과대평가하게 됩니다. 자세한 비교는
[P1 직접 대 게이트웨이](../P1_direct_vs_gateway.md)를 보십시오.

## 3. 측정을 무효로 만들 수 있었던 요인과 통제 방법

이 절이 이 부록의 핵심입니다. 아래 4개를 통제하지 않으면 **숫자가 나오지만 틀립니다.**

### 3.1 prefix 캐시 오염 — 두 번째 요청부터 빨라진다

vLLM 은 프롬프트 접두사가 같으면 프리필을 재사용합니다. 같은 프롬프트를 반복 발사하면
두 번째부터 지연이 크게 줄어 **결과가 부풀려집니다.**

**통제**: 캐시 이득 자체를 측정하는 항목을 제외한 **모든 요청의 프롬프트 앞에 고유 UUID 접두사**를
붙였습니다. 고객이 자기 환경에서 측정할 때도 같은 처리가 필요합니다.

### 3.2 출력 길이 변동 — 측정하려는 차이를 덮는다

토큰 1개당 약 21.6 ms 이므로, 요청마다 출력이 수십 토큰만 달라져도 수백 ms 가 흔들립니다.
게이트웨이 오버헤드는 수십 ms 이므로 **완전히 묻힙니다.** 실제로 출력을 고정하지 않은 조건에서는
차이의 부호가 뒤집혔습니다(−1.0720 ~ +0.7162초, 12쌍 중 양수 8건).

**통제**: 부하 시험과 오버헤드 측정은 `ignore_eos: true` 로 출력 토큰을 **정확히 고정**했습니다
(200토큰 또는 256토큰). 이 파라미터가 게이트웨이를 통과해 실제로 적용되는지 사전 확인했고,
전 구간에서 `completion_tokens` 가 지정값과 정확히 같았습니다.

⚠️ **고정 조건의 응답 내용에는 의미가 없습니다.** 실사용 지연은 고정하지 않은 측정
(P2 의 체감 지연 절)에서 가져와야 합니다.

### 3.3 인증 오버헤드 혼입

요청마다 외부 프로세스를 호출해 토큰을 얻으면 그 시간이 지연에 섞입니다.

**통제**: 캠페인 전용 토큰을 **미리 발급**해 정적 Bearer 헤더로 고정했습니다. 캠페인 종료 후
해당 토큰은 폐기했습니다.

### 3.4 외부 트래픽 혼입

같은 엔드포인트에 다른 트래픽이 섞이면 지연과 처리량이 모두 왜곡됩니다.

**통제 — 두 가지 검사를 했습니다.**

- **단발 측정**: 표본에서 **토큰당 시간**이 비정상인 것을 찾았습니다 → **0건**
- **부하 측정**: `/metrics` 의 `vllm:num_requests_running` 을 3초 간격으로 기록해 발사한 동시성보다
  큰지 대조했습니다 → 최댓값이 **정확히 32.0**(= `--max-num-seqs`)이어서 외부 요청이 배치에
  들어오지 않았음이 확인되었습니다

고객 환경에서 부하 시험을 할 때도 `/metrics` 를 함께 기록하시면 같은 검증이 가능합니다.

## 4. 측정 도구 자체를 먼저 시험했습니다

"통과한 검사" 가 아무것도 검사하지 않을 수 있습니다. 그래서 네트워크 없이 도는 자기 시험을
먼저 통과시켰습니다(**24/24**). 특히 다음 세 가지는 **실패해야 하는 입력을 넣어 실제로 실패하는지**
확인했습니다.

| 시험 항목 | 통과하지 못하면 어떤 수치가 틀리는가 |
|---|---|
| **SSE 델타 파싱** — OpenAI 호환 델타는 `choices[0].delta` 입니다. 최상위 `delta` 로 읽으면 항상 빈 값이 되어 TTFT 만 남고 본문·추론 구분이 사라집니다 | 체감 지연(TTFCT) 전체 |
| **조용한 실패 판별식** — 하네스가 **빈 본문 건수**를 세기 위한 분류 기준입니다(`finish_reason == "length"` 이면서 본문이 빈 경우). ⚠️ **고객 감지 코드는 이 조건을 쓰면 안 됩니다** — 조건을 붙이면 절단된 응답을 놓칩니다([P2 §1.5](../P2_agent_workload.md)). `finish_reason == "tool_calls"` 인 빈 본문(정상)과 `stop` 인 빈 본문(다른 원인)을 잘못 세지 않는지 확인했습니다 | 도구 호출 성공률 전체 |
| **백분위 계산 · 장문 문서 생성** — 알려진 입력으로 nearest-rank 백분위를 검산하고, 같은 seed 로 같은 문서가 생성되는지와 바늘 삽입 위치를 확인했습니다 | 모든 p50·p95 값 |

**고객 환경에서 성능을 측정하실 때도 계측 코드를 먼저 시험하시기를 권합니다.** 특히 첫 항목은
스트리밍 지연을 재는 코드에서 흔히 발생하는 오류이며, 발생하면 **TTFT 는 정상으로 보이지만
체감 지연을 완전히 놓칩니다.**

## 5. 무효 데이터 배제 — 133건

**측정 도중 vLLM 서버가 계획 없이 한 번 재기동되었습니다.** 그 구간의 요청은 전부 502 가 되었고
집계에서 배제했습니다.

| 항목 | 실측 |
|---|---|
| 상류 다운타임 | **2026-09-09 06:25:20 ~ 06:26:05 UTC (45초)** · 복구 확인 06:26:09 |
| 무효화된 요청 | **133건 전부 HTTP 502** (`longctx` 32건 전량 + `latency2` 101건) |
| 그중 즉시 실패 | **132건 · 지연 0.037 ~ 0.314초** — 프롬프트가 **52자든 288,537자든** 무관 |
| 진행 중이던 요청 | **1건 · 28.47초 뒤 502** (생성 도중 서버가 죽은 요청) |
| 그 동안 엔드포인트 상태 | **계속 `READY`** |

배제 방법: 요청마다 기록된 타임스탬프로 다운타임 구간을 잘라냈습니다. 해당 모듈은 재측정했고,
재측정분만 집계에 들어갔습니다. 배제 규칙은 집계 스크립트 안에 코드로 남아 있어 재현 가능합니다.

**이 사고에서 고객 운영에 직접 쓰이는 값이 나왔습니다** — 웜 재기동 45초, 재기동 중 502 는 프롬프트
크기와 무관하게 즉시 떨어진다는 것, 그리고 **엔드포인트 상태가 `READY` 여도 상류는 죽어 있을 수
있다는 것**입니다. [부록 B3 실패 모드](B3_failure_modes.md)에 정리했습니다.

또한 이 사고 이후 각 측정 모듈 진입부에 **상태가 아니라 실제 호출로 판정하는 사전 점검**을 넣었습니다
(driver-proxy `/health` 200 **및** 게이트웨이 `invocations` 200 을 둘 다 요구). 사고 당시 측정
스크립트는 **정상 종료(exit 0)** 했고 엔드포인트는 `READY` 였으므로, **상태만 보면 사고를 알 수
없었습니다.** 고객의 헬스체크도 같은 방식이어야 합니다.

## 6. 응답 형식 — 측정으로 확정한 필드명

클라이언트 코드에 직접 영향을 주는 항목입니다.

| 항목 | 실측 |
|---|---|
| 추론 내용 필드 | **`message.reasoning`** (스트리밍 델타도 `reasoning`. `reasoning_content` 가 **아닙니다**) |
| 추론 토큰 수 | `usage.completion_tokens_details.reasoning_tokens` |
| `content` 오염 | `<think>` 유출 **없음** |
| `cached_tokens` | 필드는 있으나 **값이 항상 `None`** 입니다 (해당 필드를 가진 원시 레코드 1,273건 전수) — prefix 캐시 적중은 `/metrics` 로만 확인 가능 |
| 통과하는 부가 파라미터 | `ignore_eos` · `min_tokens` · `response_format` · `temperature` · `seed` 모두 200 |
| `model` 필드 | 게이트웨이가 `external_model.name` 으로 **덮어씁니다** — 클라이언트가 틀려도 200 |

**`completion_tokens` 는 추론 토큰을 포함한 총 출력 토큰입니다.** 즉 `reasoning_tokens` 는
`completion_tokens` 의 부분집합이며 다음 관계가 성립합니다.

```
본문 토큰 수 = completion_tokens − reasoning_tokens
```

비용과 예산을 계산할 때 이 관계를 놓치면 실제 소비량을 과소평가합니다.
자세한 영향은 [P2 §추론 토큰 예산](../P2_agent_workload.md)을 보십시오.

## 7. 조건별 rate limit 설정

측정 항목에 따라 게이트웨이 rate limit 을 달리 두었습니다. 결과를 해석할 때 필요합니다.

| 측정 항목 | rate limit |
|---|---|
| 동시성 스윕 (처리량) | **600 calls/분으로 상향** — 한도가 아니라 GPU 를 재기 위해. 직후 원복 |
| 429 시험 · 신뢰성 시험 | **기본 120 calls/분** |
| 그 외 전 항목 | **기본 120 calls/분** |
