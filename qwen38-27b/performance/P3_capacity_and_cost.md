# P3 — 용량 산정과 비용

**측정 대상**: `Qwen/Qwen3.8-27B` 사전양자화 FP8 · vLLM 0.28.0 · A100 80GB × 1 · Azure Databricks  
**부하 조건**: closed-loop — 워커 N개가 각각 30초간 연속 발사해 진짜 동시성 N 유지 · 출력 **256토큰 고정**(`ignore_eos`) · 프롬프트 약 120토큰 · 요청마다 고유 접두사로 prefix 캐시 무효화  
**비용 기준**: `Standard_NC24ads_A100_v4` koreacentral 온디맨드 **4.959 USD/시간** (Azure Retail Prices API · 2026-09-09 조회)

> 모든 계산을 **각 항에 단위를 붙인 식으로 노출**했습니다. 값만 바꿔 귀사 워크로드로 다시 계산하실 수 있습니다.

---

## 1. 한 장 요약 — 이 GPU 1장이 감당하는 것

1. **처리량** — 권장 운영점 **N=32** 에서 **3.274 req/s = 196.4 req/분** · **838.0 출력토큰/초** 입니다(출력 256토큰 고정 조건). 그 위에서는 처리량이 정체하는데 p95 가 2배가 됩니다.
2. **비용** — 백만 출력토큰당 **1.64 USD** · 요청당 **0.000421 USD** 입니다(출력 256토큰 · N=32 조건).
3. **먼저 걸리는 것** — 짧은 응답 워크로드에서는 GPU 가 아니라 게이트웨이 기본 한도 **120 calls/분**이 먼저 걸립니다.

## 2. 동시성 스윕 — 권장 운영점은 N=32

| 동시성 N | 유효 표본 | p50 | p95 | p99 | 처리량 | 출력토큰/초 | 직전 대비 이득 |
|---|---|---|---|---|---|---|---|
| 1 | 4 | 6.142초 | 6.224초 | 6.224초 | 0.162 req/s | 41.6 | — |
| 2 | 8 | 6.188초 | 6.411초 | 6.411초 | 0.320 req/s | 81.8 | +96.8 % |
| 4 | 16 | 6.390초 | 6.446초 | 6.446초 | 0.626 req/s | 160.3 | +95.9 % |
| 8 | 32 | 6.953초 | 6.993초 | 7.001초 | 1.150 req/s | 294.4 | +83.7 % |
| 16 | 48 | 8.037초 | 8.083초 | 8.084초 | 1.990 req/s | 509.3 | +73.0 % |
| 24 | 72 | 8.866초 | 8.888초 | 8.910초 | 2.706 req/s | 692.8 | +36.0 % |
| **32** | 94 | **9.646초** | **9.671초** | 18.850초 | **3.274 req/s** | **838.0** | +21.0 % |
| 48 | 96 | 9.862초 | **18.880초** | 18.888초 | 3.457 req/s | 884.9 | **+5.6 %** |

각 레벨의 첫 N건은 워밍업으로 제외했고 전 레벨 `completion_tokens` 평균 256.0 으로 출력 고정을 확인했습니다. 이 스윕 동안만 rate limit 을 600/분으로 올렸고 직후 원복했습니다(전 레벨 429 = 0건).

**처리량 산출 방법** — 닫힌 루프(워커 N개가 응답을 받는 즉시 다음 요청을 보냄)이므로 처리량은
Little 법칙으로 정확히 구합니다.

```
처리량 X = N [워커] ÷ 평균 응답시간 R [초/요청]
  단위 검산: 워커 ÷ (초/요청) = 워커 × 요청/초 → 요청/초  ✓  (워커는 무차원 개수)
N=32 : 32 ÷ 9.775초 = 3.274 요청/초        출력토큰/초 = 3.274 × 256 = 838.0
N=1  : 1 ÷ 6.160초  = 0.162 요청/초        출력토큰/초 = 0.162 × 256 =  41.6
```

N=1 로 검산하면 방법이 맞는지 바로 보입니다 — 워커 1개가 매 요청 약 6.16초를 쓰고 요청마다
정확히 256토큰을 내므로 처리량은 `1 ÷ 6.16 = 0.162 req/s` 이고 `256 ÷ 6.16 = 41.6 출력토큰/초`
외의 값이 될 수 없습니다.

**포화 판정 근거** — N 을 32 에서 48 로 올려도 처리량은 **거의 늘지 않는데 꼬리 지연만 두 배가
됩니다.**

```
처리량 변화 = (3.457 req/s − 3.274 req/s) ÷ 3.274 req/s = +0.056 = +5.6 %
p95 변화    = 18.880초 ÷ 9.671초 = 1.95배   (거의 정확히 2배)
직전 이득   = 24→32 에서 +21.0 % → 32→48 에서 +5.6 % 로 꺾임
```

즉 **동시성 32 가 처리량의 상한은 아니지만, 그 이상에서는 지불 대비 이득이 급격히 나빠집니다.**
동시성 50 % 를 더 넣어 처리량 5.6 % 를 얻는 대신 p95 를 2배로 만드는 교환입니다.

> ⚠️ **권장 운영점 N=32 에서도 꼬리는 이미 갈라져 있습니다.** 같은 표에서 N=32 의 p95 는
> 9.671초인데 **p99 는 18.850초**입니다 — 상위 약 1 %는 이미 배치 라운드를 한 번 더 기다립니다.
> 다만 유효 표본이 94건이므로 **이 p99 는 관측 1건**이며, 비율로 일반화할 수 없습니다.
> **p99 를 SLA 로 약속해야 한다면 동시성을 32 보다 낮게 잡으십시오** — N=24 의 p99 는 8.910초로
> p95(8.888초)와 거의 같습니다.

**p95 가 정확히 두 배가 되는 것이 원인을 말해 줍니다.** `--max-num-seqs 32` 이므로 GPU 는 한 번에 32 시퀀스만 돌립니다. 배치 라운드 한 번이 약 9.6초이고, 슬롯을 못 잡은 요청은 **한 라운드를 그대로 기다립니다.** N=48 에서 나온 +5.6 % 는 대기열이 항상 차 있어 슬롯이 비는 순간이 줄어든 효과로 보이지만 **규명하지 않았습니다.** **동시성 목표는 32 로 두십시오** — 근거는 "그 위에서 처리량이 줄어든다" 가 아니라 **"처리량은 정체하는데 p95 가 2배가 된다"** 입니다.

### 2.1 배치 효율 — 개별 요청은 조금 느려지고 전체 처리량은 크게 늡니다

| 항목 | N=1 | N=32 | 배수 |
|---|---|---|---|
| 처리량 | 0.162 req/s | 3.274 req/s | **20.2배** |
| 출력토큰/초 | 41.6 | 838.0 | **20.2배** |
| 지연 p50 | 6.142초 | 9.646초 | 1.57배 |

```
처리량 배수 = 3.274 req/s ÷ 0.162 req/s = 20.2   (단위: (req/s)/(req/s) = 무차원)
지연 배수   = 9.646초 ÷ 6.142초 = 1.57           (단위: 초/초 = 무차원)
```

**개별 요청이 1.57배 느려지는 대가로 전체 처리량이 20.2배가 됩니다.** GPU 비용은 시간당 고정이므로 비용 효율도 그대로 20.2배입니다(§4.1). **배치를 채우지 않으면 이 GPU 능력의 95 %를 버립니다.**

## 3. 병목은 KV 캐시가 아니라 배치 슬롯입니다

부하 중 `/metrics` 를 3초 간격으로 98회 스냅샷했습니다.

| 지표 | 최댓값 | p50 | 의미 |
|---|---|---|---|
| `vllm:num_requests_running` | **32.0** | 9.0 | 정확히 `--max-num-seqs 32`. **한 번도 넘지 않았습니다** |
| `vllm:num_requests_waiting` | **16.0** | 0.0 | 정확히 48 − 32. 초과분이 큐에서 대기 |
| `vllm:kv_cache_usage_perc` | **0.15041 (15.041 %)** | 0.04583 | KV 는 **85 % 가 남아 있습니다** |
| `vllm:num_preemptions_total` | **0** | 0 | 선점·스왑 없음 |

`running` 이 정확히 32 에서 멈추고 `waiting` 이 초과분과 정확히 일치하는데 **KV 는 15 %만 쓰였고 선점은 0건**입니다. 처리량을 제한한 것은 메모리가 아니라 **동시 처리 슬롯 수**입니다.

### 3.1 튜닝 여지는 가설입니다 — 측정하지 않았습니다

> **⚠️ 아래는 가설이며 이 캠페인에서 측정되지 않았습니다.** KV 가 15 %만 쓰이므로 짧은 컨텍스트 워크로드에서는 `--max-num-seqs` 를 32 보다 올려 처리량을 더 얻을 여지가 있어 **보입니다.** 그러나 `--max-num-batched-tokens 7840` 이 별도 상한으로 작용할 수 있고 검증에는 vLLM 재기동이 필요해 **시험하지 않았습니다.** 이 문서의 산정식은 전부 `--max-num-seqs 32` 실측 위에 있습니다.

**귀사 환경에서 이 가설을 시험하는 방법**  
· `--max-num-seqs` 를 **64** 로 바꿔 재기동한 뒤 위 스윕(N = 1·8·16·32·48·64, 각 30초, `ignore_eos` + `max_tokens: 256`)을 반복합니다.  
· 부하 중 `/metrics` 를 3초 간격으로 기록해 **`num_requests_running` 최댓값이 실제로 64 까지 오르는지** 봅니다. 32 근처에서 멈추면 `--max-num-batched-tokens` 가 진짜 상한입니다.  
· **처리량이 늘어도 p95 가 함께 뛰면 이득이 아닙니다.** 둘을 같이 보고, 필요하면 96 으로 반복해 다시 꺾이는 지점을 찾습니다.

### 3.2 귀사 배포에서 병목을 진단하는 방법

`/metrics` 는 vLLM 이 직접 노출하므로 **driver-proxy 경로**(`.../driver-proxy-api/o/<조직ID>/<클러스터ID>/8005/metrics`)로 읽습니다. 게이트웨이 엔드포인트는 `invocations` 만 노출합니다. **반드시 부하 중에 3초 간격으로 뽑아야 최댓값이 잡힙니다**(부하 후 스냅샷은 전부 0). `running` 최댓값이 발사한 동시성보다 크면 **다른 트래픽이 섞인 것**이므로 측정을 무효로 처리하십시오.

| 관측 조합 | 병목 | 조치 |
|---|---|---|
| `running` 이 `--max-num-seqs` 값에 붙어 있고 `kv_cache_usage_perc` 가 낮음 | **배치 슬롯** (이 측정과 동일) | §3.1 의 가설 시험 |
| `kv_cache_usage_perc` 가 0.9 이상으로 오름 | **KV 캐시** | `--max-model-len` 또는 컨텍스트 축소 |
| `num_preemptions_total` 이 0 보다 큼 | **KV 압박** (요청 선점·스왑) | 동시성·컨텍스트 축소 |
| `waiting` 이 지속적으로 0 보다 큼 | **유입이 처리 능력 초과** | GPU 증설 또는 유입 조절 |
| `running` 은 낮은데 지연이 큼 | **프리필** (장문) | [부록 B2](appendix/B2_long_context_rag.md) |
| 전부 정상인데 429 가 보임 | **게이트웨이 한도** | §6 |

## 4. 비용 모델

### 4.1 기준 단가와 백만 출력토큰당 비용

```
0.0013775 USD/초 = 4.959 USD/시간 ÷ 3,600 초/시간
  단위 검산: USD/시간 ÷ (초/시간) = USD/시간 × 시간/초 = USD/초  ✓

N=1  (배치 없음) : 0.0013775 USD/초 ÷  41.6 출력토큰/초 × 1,000,000 출력토큰 = 33.15 USD
N=32 (권장 운영점): 0.0013775 USD/초 ÷ 838.0 출력토큰/초 × 1,000,000 출력토큰 =  1.64 USD
  단위 검산: (USD/초) ÷ (출력토큰/초) = USD/초 × 초/출력토큰 = USD/출력토큰
             USD/출력토큰 × 출력토큰 = USD  ✓

비용 비 = 33.15 USD ÷ 1.64 USD = 20.2   (= 838.0 ÷ 41.6 = 20.1 — 처리량 배수와 일치)
```

이 GPU 는 **요청이 없어도 초당 0.0013775 USD 를 씁니다.** 그래서 **같은 GPU · 같은 시간 단가인데 백만 토큰당 비용이 20배 차이납니다.** 차이를 만든 것은 하드웨어가 아니라 **배치가 채워졌는지**입니다. 동시성 1로 쓰는 배포는 33.15 USD 를, 32로 쓰는 배포는 1.64 USD 를 냅니다. **용량 계획에서 가장 큰 비용 레버는 동시성입니다.**

### 4.2 요청당 비용

```
0.000421 USD/요청 = 0.0013775 USD/초 ÷ 3.274 요청/초
  단위 검산: (USD/초) ÷ (요청/초) = USD/초 × 초/요청 = USD/요청  ✓
교차 검산: 0.000421 USD/요청 ÷ 256 출력토큰/요청 × 1,000,000 출력토큰 = 1.64 USD  ← §4.1 과 일치  ✓
```

즉 **1,000 요청에 0.42 USD** · **100만 요청에 421 USD** 입니다(출력 256토큰 · N=32).

### 4.3 ⚠️ 일반화 한계 — 출력 256토큰 고정 조건입니다

이 절의 모든 값은 **출력 토큰을 정확히 256 으로 고정한** 부하 시험에서 나왔습니다. **출력 길이가 다르면 값이 달라지며, 이 캠페인은 출력 길이별 비용을 일반화하지 않았습니다.** 지연이 출력 토큰 수에 선형이라는 별도 관측은 있으나(예산 800·2,000·4,000·6,000 에서 약 46 tok/s 일정), **다른 출력 길이에서 백만 토큰당 비용이 같다는 것은 직접 시험하지 않았습니다.** 특히 출력이 256 보다 훨씬 짧으면 요청당 고정 비용(프리필·스케줄링) 비중이 커지는데 그 영역은 미측정입니다. → [부록 B5 한계](appendix/B5_limitations.md)

### 4.4 지불하는 토큰의 대부분이 본문이 아닙니다

추론 토큰은 `completion_tokens` 에 포함되어 **과금 대상 출력 토큰이 됩니다.** `1+1은? 숫자만 답하라` 라는 가장 사소한 질문조차 **출력 82토큰 중 78토큰(95.1 %)이 추론**이었고 본문은 4토큰이었습니다(n=6).

```
본문 비중 = 1 − 0.951 = 0.049  [본문토큰/출력토큰]
본문 백만토큰당 비용 = 1.64 USD/백만 출력토큰 ÷ 0.049 [본문토큰/출력토큰] = 33.5 USD/백만 본문토큰
  단위 검산: (USD/출력토큰) ÷ (본문토큰/출력토큰) = USD/출력토큰 × 출력토큰/본문토큰 = USD/본문토큰  ✓

같은 계산을 산수 서술형(추론 비중 63.1 %)에 적용: 1.64 ÷ 0.369 = 4.44 USD/백만 본문토큰
```

**질문 유형에 따라 "실제로 쓸 수 있는 토큰" 의 단가가 7.5배 차이납니다**(6.59 대 49.6). 견적을 본문 길이 기준으로 세우면 크게 어긋납니다. **견적은 `completion_tokens` 기준으로 세우고 질문 유형별 추론 비중을 먼저 측정하십시오.** 추론 폭주(예산 전량을 추론에 쓰고 본문 0자로 끝나는 실패)는 이 비용을 **전액 낭비**로 만듭니다 — `max_tokens=6000` 에서 **130.3초를 쓰고 본문 0자**인 사례가 실측되었습니다. 감지와 대응은 [P2 Agent 워크로드](P2_agent_workload.md) · [부록 B3 실패 모드](appendix/B3_failure_modes.md) 를 보십시오.

## 5. 용량 산정 — 두 제약을 모두 확인해야 합니다

성격이 다른 두 병목이 있고 **둘 중 큰 쪽이 필요 GPU 수를 결정합니다.** 한쪽만 계산하면 장문 RAG 에서는 39배 과소 산정됩니다.

```
제약 ① 디코드(출력) : 838.0 출력토큰/초 × 60 초/분 = 50,280 출력토큰/분/GPU
제약 ② 프리필(입력) : 1,800 입력토큰/초 × 60 초/분 = 108,000 입력토큰/분/GPU
  단위 검산: (출력토큰/초) × (초/분) = 출력토큰/분  ✓
```

**제약 ①** 은 위 §2 의 N=32 실측값입니다. **제약 ②** 는 두 실측 중 **작은 쪽**입니다 — 단일 요청 100K 구간 1,802 tok/s 와 32K 문서 4건 동시 발사의 집계 1,840 tok/s. 두 값이 거의 같다는 사실 자체가 중요합니다: **프리필은 동시에 보내도 총량이 그대로 걸리며 병렬 이득이 없습니다.** §2.1 의 배치 효율(출력 20배)은 프리필에 적용되지 않으므로, 프리필은 **GPU 1장이 가진 하나의 총예산**으로 다룹니다.

### 5.1 절차

```
입력 변수
  M = 동시 사용자 수        [사용자]            I = 요청당 입력 토큰  [입력토큰/요청]
  R = 사용자당 분당 요청 수  [요청/(사용자·분)]   O = 요청당 출력 토큰  [출력토큰/요청]

1) 요청률          = M × R                              [요청/분]
2) 필요 GPU(디코드) = ceil( (M × R × O) ÷ 50,280 )   ← (출력토큰/분) ÷ (출력토큰/분/GPU) = GPU  ✓
3) 필요 GPU(프리필) = ceil( (M × R × I) ÷ 108,000 )  ← (입력토큰/분) ÷ (입력토큰/분/GPU) = GPU  ✓
4) 필요 GPU        = max( 2), 3) )
5) rate limit 확인 : 1) 의 요청률 [요청/분] 이 게이트웨이 한도 [calls/분] 아래인지 (§6)
```

**`I` 는 prefix 캐시가 듣지 않는 부분만 셉니다.** 같은 문서에 질문만 바꾸는 설계라면 프리필이 12.7~23.2배 줄어들므로 보수적으로 `문서토큰 ÷ 12.7` ~ 낙관적으로 `문서토큰 ÷ 23.2` 사이로 잡습니다. 예시 3′ 는 중간값 `÷ 15` 를 썼습니다.

### 5.2 예시

**예시 1 — 사내 챗봇 (짧은 대화형 agent)** · `M=50 · R=5 · O=256 · I=500`

```
요청률   = 50 × 5 = 250 요청/분
디코드   = (50 × 5 × 256) 출력토큰/분 ÷ 50,280 출력토큰/분/GPU =  64,000 ÷  50,280 = 1.27 → 2 GPU
프리필   = (50 × 5 × 500) 입력토큰/분 ÷ 108,000 입력토큰/분/GPU = 125,000 ÷ 108,000 = 1.16 → 2 GPU
필요 GPU = max(2, 2) = 2 GPU · 두 제약이 같음 · rate limit 250 > 120 → 한도 상향 필요
```

**예시 2 — 대규모 agent (긴 응답)** · `M=200 · R=8 · O=512 · I=1,000`

```
요청률   = 200 × 8 = 1,600 요청/분
디코드   =   819,200 출력토큰/분 ÷  50,280 출력토큰/분/GPU = 16.30 → 17 GPU
프리필   = 1,600,000 입력토큰/분 ÷ 108,000 입력토큰/분/GPU = 14.81 → 15 GPU
필요 GPU = max(17, 15) = 17 GPU · 지배 제약 디코드 · 한도를 최소 1,600 이상으로
```

**예시 3 — 장문 문서 RAG (32K 문서 · prefix 캐시 미적중)** · `M=50 · R=1 · O=256 · I=32,000`

```
요청률   = 50 × 1 = 50 요청/분
디코드   =    12,800 출력토큰/분 ÷  50,280 출력토큰/분/GPU =  0.25 →  1 GPU
프리필   = 1,600,000 입력토큰/분 ÷ 108,000 입력토큰/분/GPU = 14.81 → 15 GPU
필요 GPU = max(1, 15) = 15 GPU · 지배 제약 프리필 · 프리필 ÷ 디코드 = 14.81 ÷ 0.25 = 58.2배
```

**출력만 계산하면 1장, 프리필까지 계산하면 15장입니다.** 장문 RAG 에서 한쪽만 보면 58배 어긋납니다.

**예시 3′ — 같은 RAG · prefix 캐시가 듣는 설계** (문서 고정 · 질문만 변경)

```
실질 프리필 = 32,000 입력토큰/요청 ÷ 15 = 2,133 입력토큰/요청
프리필   = (50 × 1 × 2,133) 입력토큰/분 ÷ 108,000 입력토큰/분/GPU = 106,650 ÷ 108,000 = 0.99 → 1 GPU
필요 GPU = max(1, 1) = 1 GPU        GPU 수 변화: 15 GPU → 1 GPU = 15배 감소
```

> **RAG 에서 prefix 캐시 재사용 여부가 필요 GPU 수를 15배 바꿉니다**(예시 3 대 3′). 이 배포에서 아키텍처 결정이 비용에 가장 크게 작용하는 지점입니다. 캐시가 실제로 듣는지는 응답의 `cached_tokens` 로 알 수 없으므로(항상 `None`) `/metrics` 의 `vllm:prefix_cache_hits_total` 로 확인하십시오. → [부록 B2](appendix/B2_long_context_rag.md)

**예시 4 — 도구 호출 루프 (요청 수가 많은 워크로드)** · `M=30 · 턴 4회/분 × 5홉 = R=20 · O=180 · I=1,200`  
사용자 턴 1회가 도구 호출 5홉을 유발하므로 **요청 수가 사용자 턴 수의 5배**이고, 홉마다 대화가 누적됩니다.

```
요청률   = 30 × 20 = 600 요청/분
디코드   = (30 × 20 ×   180) 출력토큰/분 ÷  50,280 = 108,000 ÷  50,280 = 2.15 → 3 GPU
프리필   = (30 × 20 × 1,200) 입력토큰/분 ÷ 108,000 = 720,000 ÷ 108,000 = 6.67 → 7 GPU
필요 GPU = max(3, 7) = 7 GPU · 지배 제약 프리필 · rate limit 600 = 기본 한도의 5배
```

**사용자 턴 수로 용량을 잡으면 5배 과소 산정됩니다.** 홉마다 누적 대화를 다시 보내므로 프리필이 지배 제약이 됩니다.

**예시 5 — 소수 사용자 고빈도 (배치 문서 처리)** · `M=5 · R=40 · O=300 · I=600`

```
요청률   = 5 × 40 = 200 요청/분
디코드   =  60,000 출력토큰/분 ÷  50,280 출력토큰/분/GPU = 1.19 → 2 GPU
프리필   = 120,000 입력토큰/분 ÷ 108,000 입력토큰/분/GPU = 1.11 → 2 GPU
필요 GPU = max(2, 2) = 2 GPU · 두 제약이 같음 · rate limit 200 > 120 → 한도 상향 필요
```

사용자가 5명뿐인데 GPU 2장이 필요합니다. **용량을 결정하는 것은 사용자 수가 아니라 분당 토큰 처리량**입니다.

## 6. rate limit 이 GPU 보다 먼저 걸립니다

### 6.1 교차점 — 출력 419토큰에서 뒤집힙니다

```
GPU 가 낼 수 있는 요청률 = 50,280 출력토큰/분 ÷ O 출력토큰/요청
  단위 검산: (출력토큰/분) ÷ (출력토큰/요청) = 출력토큰/분 × 요청/출력토큰 = 요청/분  ✓

교차 조건: 50,280 출력토큰/분 ÷ O 출력토큰/요청 = 120 요청/분
       O = 50,280 출력토큰/분 ÷ 120 요청/분 = 419 출력토큰/요청
  단위 검산: (출력토큰/분) ÷ (요청/분) = 출력토큰/분 × 분/요청 = 출력토큰/요청  ✓
```

| 평균 출력 O | GPU 요청률 상한 | 기본 한도 120/분 대비 | 먼저 걸리는 것 |
|---|---|---|---|
| 128 출력토큰/요청 | 392.8 요청/분 | 초과 | **rate limit** |
| 256 출력토큰/요청 | 196.4 요청/분 | 초과 | **rate limit** (N=32 실측 조건) |
| **419 출력토큰/요청** | **120.0 요청/분** | **동일** | **교차점** |
| 512 출력토큰/요청 | 98.2 요청/분 | 미달 | **GPU** |

**평균 출력이 419토큰보다 짧으면 한도가 먼저, 길면 GPU 가 먼저 걸립니다.** 실측으로도 대조됩니다 — `max_tokens=1500` 으로 200건을 발사한 시험은 195.54초(= **61 요청/분**)가 걸렸고 **429 는 0건**이었습니다. 출력 생성이 먼저 병목이 되어 한도에 도달조차 못 한 것입니다.

> ⚠️ 이 표는 **출력 256토큰에서 측정한 디코드 상한(50,280 출력토큰/분)을 나눈 값**입니다. 출력이 256 에서 멀어질수록 요청당 고정 비용의 영향이 커지는데 그 영역은 측정되지 않았습니다. **직접 측정된 요청률은 196.4 요청/분(출력 256토큰 · N=32) 하나뿐입니다.**

### 6.2 한도는 정확히 120 에서 끊기지 않습니다

한도를 기본값 120/분으로 둔 상태에서 400건을 한꺼번에 발사했습니다.

| 항목 | 실측 |
|---|---|
| 발사 | **400건** · `max_tokens=1`(의도적으로 최소 출력) · wall **5.25초** · 실효 발사율 **4,572.9 요청/분** |
| HTTP 200 / HTTP 429 | **133건** / **267건** |
| 429 응답 코드 · 헤더 | `error_code: REQUEST_LIMIT_EXCEEDED` · **`Retry-After` 없음**(`content-type`·`server`·`x-request-id`·`x-databricks-org-id` 만) |
| 429 지연 | p50 0.184초 (범위 0.096~0.253초) — 즉시 거절 |
| 회복 | +0초 **429** → **+10초부터 200** (이후 90초까지 계속 200) |

```
한도 초과 통과량 = 133건 ÷ 120 calls/분 = 1.108  →  한도보다 약 11 % 많이 통과
```

**한도가 120 인데 133건이 통과했습니다.** 클라이언트가 한도를 정확한 값으로 신뢰해 자체 유량 제어를 설계하면 어긋납니다. **429 처리 경로가 반드시 있어야 하며 `Retry-After` 가 없으므로 백오프는 클라이언트가 직접 구현해야 합니다.** → [부록 B3 실패 모드](appendix/B3_failure_modes.md)

### 6.3 한도를 올리는 방법과 함께 확인할 것

한도는 서빙 엔드포인트의 AI Gateway 설정 `rate_limits`(`{"calls": 120, "renewal_period": "minute", "key": "endpoint"}`)에 있습니다. `calls` 값을 바꿔 갱신합니다 — 절차는 [배포 가이드 STEP4](../deployment/STEP4_ai_gateway.md) 에 있습니다.

· **필요 한도 ≥ §5 의 요청률.** 예시 4는 600 요청/분이므로 기본 120 은 5배 부족합니다.  
· **한도만 올려도 GPU 포화점은 그대로입니다.** 429 가 사라지는 대신 요청이 큐에 쌓여 p95 가 뛰고(§2 의 N=48 사례) 사용자는 429 대신 타임아웃을 봅니다. **한도와 GPU 수를 함께 올리십시오.**  
· **여유를 두십시오.** §6.2 대로 한도가 정확히 끊기지 않으므로 필요 요청률에 딱 맞춘 값은 위험합니다.  
· **`key: endpoint`** 이므로 한도는 엔드포인트 단위입니다. 한 클라이언트의 버스트가 같은 엔드포인트를 쓰는 다른 클라이언트를 429 로 밀어냅니다.  
· 평균 출력이 256토큰 이하이고 동시성 24 이상을 쓸 계획이면 **최소 200/분**으로 올리십시오. 그렇지 않다면 기본 120/분으로 충분합니다.

## 7. 스케일 아웃 — 이 캠페인이 측정하지 않은 것

**이 캠페인은 A100 80GB × 1, 단일 클러스터, 단일 리전(Azure koreacentral), 단일 시점만 측정했습니다.** §5 의 산정식은 **GPU 1장 실측값을 나눈 것**이며, 여러 장으로 늘렸을 때 처리량이 선형으로 늘어나는지는 **측정하지 않았습니다.** 15장이 필요하다는 계산은 "1장의 15배가 필요하다" 는 뜻이며 "15장을 붙이면 15배가 나온다" 는 측정 결과가 아닙니다.

**측정하지 않은 것**  
· 2장 이상에서의 처리량 선형성 · 분배 계층(로드밸런서)의 오버헤드 · 다중화 시 지연 분포  
· 장시간 지속 운영 — 이 캠페인의 각 부하 레벨은 **30초**입니다 · 리전 간 차이 · 다른 시간대의 클라우드 혼잡

**구조상 따라오지만 측정되지 않은 것** (설계 시 확인하십시오)  
· vLLM 은 클러스터 드라이버 프로세스 1개에 뜨므로 **GPU 를 늘리는 것 = 클러스터를 늘리는 것**입니다. 이 트랙의 엔드포인트 1개는 상류 URL 1개를 가리키므로 다중화에는 별도 분배 계층이 필요합니다.  
· **prefix 캐시는 vLLM 프로세스 안에 있습니다.** 같은 문서 질의가 여러 클러스터로 흩어지면 §5.2 예시 3′ 의 15배 이득이 줄어듭니다. 문서 기준 sticky 라우팅이 필요할 수 있습니다.  
· rate limit 은 엔드포인트 단위이므로 **GPU 를 늘릴 때 한도도 함께 올려야** 합니다(§6.3).

**귀사가 확인해야 할 것**  
· 2장·4장에서 §2 와 같은 스윕을 돌려 **처리량이 실제로 배수로 늘어나는지** 확인하십시오.  
· 분배 계층을 넣은 뒤 **p95 가 얼마나 늘어나는지** 재측정하십시오. 이 값은 이 문서에 없습니다.  
· RAG 라면 분배 후의 **`vllm:prefix_cache_hits_total` 적중률**을 반드시 다시 재십시오.
