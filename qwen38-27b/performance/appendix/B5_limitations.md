# 부록 B5 · 이 측정이 증명하지 못하는 것

**이 부록이 답하는 질문**: "이 보고서를 어디까지 근거로 쓸 수 있고, 무엇을 제 환경에서 직접
확인해야 합니까?"

측정된 것과 측정되지 않은 것을 섞으면 잘못된 결정으로 이어집니다. 이 부록은 **경계를 명시**합니다.
§3 에 **고객 환경에서 재측정을 권장하는 항목**을 우선순위와 함께 정리했습니다.

---

## 1. 표본과 환경의 한계

### 1.1 단일 조건입니다

**단일 리전 · 단일 노드 · 단일 시점**입니다 — Azure koreacentral · A100 80GB **1장** ·
2026-09-09 약 1시간 36분. 다음은 측정되지 않았습니다.

- 다른 리전 · 다른 클라우드
- **GPU 여러 장 · 여러 노드로의 확장 선형성** — [P3](../P3_capacity_and_cost.md)의 용량 산정식은
  1장 실측을 나눈 값입니다. 2장이 정확히 2배가 되는지는 확인되지 않았습니다
- 다른 GPU 세대 (H100 등)
- 다른 시간대 · 장기간에 걸친 변동

### 1.2 표본이 작은 항목이 있습니다

| 항목 | 표본 |
|---|---|
| `tool_choice` 조건별 | n=3~5 |
| 멀티턴 세션 | n=5 세션 (4턴) |
| 장문 각 구간 | n=2 |
| **prefix 캐시 콜드 기준선** | **n=1** |
| 게이트웨이 오버헤드 (스트리밍 TTFT) | n=6 쌍 |
| 게이트웨이 오버헤드 (출력 고정) | n=12 쌍 |

이 규모에서의 **전수 관측**이며 비율을 일반화할 수 없습니다. 특히 **prefix 캐시 12.7~23.2배는
콜드 기준선이 1회 관측**입니다. 그 값이 독립 측정(32K TTFT 직접 측정 14.22~14.25초)과 일치하는
것으로 타당성을 확인했지만, 배수 자체는 표본 1의 기준선에 의존합니다.

### 1.3 완전히 격리된 환경은 아니었습니다

같은 클러스터를 쓰는 다른 작업이 있었습니다. 오염 검사(토큰당 시간 이상치 0건,
`num_requests_running` 최댓값이 정확히 32.0)에서 영향은 확인되지 않았으나
([부록 B1 §3.4](B1_method_and_environment.md)) 전용 환경에서의 측정은 아닙니다.

또한 측정 도중 서버가 계획 없이 한 번 재기동되어 **133건을 배제**했습니다
([부록 B1 §5](B1_method_and_environment.md)).

## 2. 측정하지 않은 것

### 2.1 성능 관련

| 항목 | 상태 | 왜 중요한가 |
|---|---|---|
| **`--max-num-seqs` 상향 여지** | **가설** — 측정하지 않았습니다 | KV 가 15 %만 쓰이므로 32 보다 올릴 여지가 보이지만 검증되지 않았습니다. 올리면 처리량이 늘 수도 있고 지연이 나빠질 수도 있습니다 |
| `--max-num-batched-tokens 7840` 의 영향 | 분리 측정하지 않았습니다 | `--max-num-seqs` 와 별도로 상한이 될 수 있습니다. 위 가설을 시험할 때 함께 봐야 합니다 |
| **출력 길이별 비용 일반화** | 출력 256토큰에서만 측정 | 백만토큰당 1.64 USD 는 이 조건의 값입니다. 지연이 출력에 선형이라는 별도 관측은 있으나 비용의 등가성은 시험하지 않았습니다 |
| 재기동 전 구간의 포화점 | 재기동 후 구간에서만 측정 | 병목이 배치 슬롯이므로 KV 용량 4.4 % 차이가 포화점을 옮기지 않을 것으로 보이나 **측정하지 않았습니다** |
| 컨텍스트 상한 근처의 정확한 성공 경계 | 104,536토큰 성공 · 그보다 큰 요청은 거절 — **그 사이는 미측정**. 거절 응답의 `129573` 은 `131072 − max_tokens + 1` 인 **하한 표시**이며 실측 토큰 수가 아닙니다 | 상한 근처를 쓰려면 직접 확인이 필요합니다 |
| prefix 캐시의 유지 시간 · 축출 정책 | 5개 질문을 연속 발사한 짧은 창에서만 관측 | 시간이 지나거나 다른 요청이 섞이면 언제 축출되는지 모릅니다. **RAG 설계에 직접 영향을 줍니다** |
| 다중 시간 지속 운영 | 각 부하 레벨이 **30초**입니다 | 장시간 부하에서의 메모리 누수 · 성능 저하는 이 측정 범위 밖입니다 |

### 2.2 기능·정확성 관련

| 항목 | 상태 |
|---|---|
| **장문 정확성의 한계 지점** | 3개 바늘 18/18 만점 = **천장효과**. 상충 정보 판별 · 전역 집계 · 더 많은 바늘은 미측정 |
| `json_object` 의 복잡한 스키마 | 3필드 단순 스키마에서 18/18. **중첩 객체 · 배열 · 선택 필드 · `json_schema` 타입은 미시험** |
| 멀티모달 | `--language-model-only` 로 기동했으므로 **이 배포에 이미지 입력은 없습니다** |
| 절단과 완전 공백의 고객 영향 차이 | 둘 다 `finish_reason == "length"` 로 잡히지만, 절단된 응답을 부분적으로 쓸 수 있는지는 과제에 따라 다르며 판정하지 않았습니다 |
| 한국어 이외 언어 | 한국어와 영어 혼용 조건만 측정했습니다 |

### 2.3 운영 관련

| 항목 | 상태 |
|---|---|
| 클라이언트 중단 시 서버 취소 여부 | **판정할 수 없었습니다.** `/metrics` 의 `num_requests_running` 이 1 → 2 로 관측돼 결론이 나지 않았습니다. 별도 실험이 필요합니다 |
| **추론 트래픽만으로 자동 종료가 발동하는지** | **직접 측정된 적이 없습니다.** 문서 근거와 별건 관측만 있습니다. `autotermination_minutes: 0` 을 권고하는 이유가 여기 있습니다 |
| 502 지연의 다른 원인 | 0.037~0.314초 즉시 실패는 **재기동 구간**에서만 측정했습니다. 프로세스 부재 · 루프백 바인드는 응답 표면이 같다는 별도 근거가 있으나 지연은 측정하지 않았습니다 |
| 폐쇄망 · Private Link · egress 제한 환경 | 이 워크스페이스는 제약이 없었습니다. **serverless egress 가 `Restricted access` 인 환경에서는 엔드포인트 등록은 되지만 호출이 `CUSTOMER_UNAUTHORIZED` 로 차단됩니다**(2026-09-10 실측). 허용 도메인 추가로는 해결되지 않으며 선택지는 [부록 A4](../../deployment/appendix/A4_serverless_egress_allowlist.md) 에 있습니다 |
| rate limit 상향의 상한 | 600/분까지만 시험했습니다 |
| PAT 회전 중 무중단 여부 | 미측정 |

## 3. 방법의 한계

- **prefix 캐시 이득은 추정값입니다.** 총 지연에서 생성 시간을 보정해 프리필을 역산했습니다.
  보정 계수(45.86 tok/s)의 안정성과, 콜드 추정값이 독립 측정 TTFT 와 일치하는 것으로 타당성을
  확인했지만 **스트리밍으로 TTFT 를 직접 재는 것이 더 정확합니다.**
- **부하 시험의 응답 내용에는 의미가 없습니다.** `ignore_eos` 로 출력을 고정했으므로 생성된
  텍스트는 무의미합니다. 실사용 지연은 [P2](../P2_agent_workload.md)의 값을 쓰십시오.
- **저장소의 8시간 연속 부하 기록은 이 보고서와 같은 모집단이 아닙니다.** 다른 구성 · 다른
  클러스터에서 측정된 것이므로 이 문서의 수치와 섞어 인용하면 안 됩니다.

## 4. 고객 환경에서 재측정을 권장하는 항목

우선순위 순입니다. **1~3번은 운영 투입 전에 확인하시기를 권합니다.**

| # | 항목 | 왜 | 어떻게 |
|---|---|---|---|
| **1** | **실제 워크로드의 추론 토큰 비율과 폭주 빈도** | 이 측정의 최대 위험이고 **과제 종류에 따라 완전히 달라집니다.** 어느 질문이 폭주할지 사전에 알 수 없습니다 | 대표 질문 50~100개를 실제 `max_tokens` 로 발사하고 `finish_reason` 분포와 `reasoning_tokens / completion_tokens` 비율을 집계하십시오 |
| **2** | **목표 워크로드의 실제 처리량** | 이 보고서의 값은 **출력 256토큰 고정** 조건입니다. 실제 입출력 길이가 다르면 값이 달라집니다 | [P3](../P3_capacity_and_cost.md)의 산정식으로 예측한 뒤, 실제 프롬프트·출력 길이로 동시성 스윕을 재실행해 대조하십시오 |
| **3** | **rate limit 이 목표 처리량에 충분한지** | 기본 120/분은 이 GPU 의 실측 196.4 req/분보다 **작습니다** | 목표 req/분을 계산해 한도를 먼저 맞추십시오 |
| 4 | 장문 정확성 (고객 데이터) | 18/18 은 **천장효과**이며 정확성 근거가 아닙니다 | 실제 문서와 실제 질문으로 평가셋을 만드십시오. 상충 정보와 전역 집계를 포함하십시오 |
| 5 | prefix 캐시 재사용률 | 재사용 여부가 **필요 GPU 수를 크게 바꿉니다**. 축출 정책은 미측정입니다 | `/metrics` 의 `vllm:prefix_cache_hits_total` · `vllm:prefix_cache_queries_total` 를 운영 중 계측하십시오 |
| 6 | 복잡한 JSON 스키마 | 3필드 단순 스키마에서만 검증되었습니다 | 실제 사용할 스키마로 100건 시험하십시오 |
| 7 | `--max-num-seqs` 상향 | **가설입니다.** 처리량 여유가 있을 수 있습니다 | 32 → 48 · 64 로 올려 동시성 스윕을 반복하고 p95 와 preemption 을 함께 보십시오 |
| 8 | 자동 종료 발동 조건 | 직접 측정된 적이 없습니다 | `autotermination_minutes: 0` 이면 확인할 필요가 없습니다. 0 이 아니라면 추론 트래픽만 흘리고 종료되는지 관측하십시오 |

## 5. 이 보고서를 인용할 때

- **조건을 함께 인용하십시오.** "3.274 req/s" 가 아니라 "동시성 32 · 출력 256토큰 고정에서
  3.274 req/s" 입니다
- **표본 수를 함께 인용하십시오.** 특히 n=1~6 항목
- **"측정하지 않았다" 를 "문제없다" 로 바꾸지 마십시오** — §2 의 항목들은 결과를 모르는 것입니다
- 장문 정확성 18/18 은 **"정확하다" 가 아니라 "이 난이도에서는 한계가 드러나지 않았다"** 입니다
