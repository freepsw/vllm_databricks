# P2. AI Agent 워크로드 — 구현 전에 반드시 알아야 할 것

**대상**: 이 엔드포인트로 AI Agent · 챗봇 · 자동화 워크플로를 구현하는 개발자  
**근거**: 2026-09-09 실측 캠페인, 유효 요청 1,553건 (원본 리포트 §3.3)  
**성격**: 관찰 보고가 아니라 **코드에 반영할 항목의 목록**입니다. 모든 수치에 표본 수를 병기했습니다.

## 0. 개발자가 반드시 구현해야 하는 3가지

1. **`finish_reason == "length"` 를 본문 유무와 무관하게 실패로 처리하십시오.** 이 배포에서 답이 없는 응답은 오류가 아니라 HTTP 200 으로 돌아옵니다 (§1).
2. **TTFT 를 SLA 로 쓰지 마십시오.** 첫 SSE chunk 는 0.271초에 오지만 사용자가 답을 보기 시작하는 시각은 p50 3.549초 · p95 7.145초입니다 (§2).
3. **`tool_choice` 로 특정 함수를 강제하지 마십시오.** 조용히 무시됩니다. 구조화 추출은 `response_format` 으로, 도구 호출 보장은 검증 루프로 처리하십시오 (§3).

## 1. 추론 토큰 예산 — 이 배포의 최대 함정

이 모델은 추론(reasoning) 모델입니다. **추론 토큰이 `max_tokens` 예산을 먼저 소비하며 `completion_tokens` 에 추론 토큰이 포함됩니다.** 예산이 모자라면 오류가 아니라 **HTTP 200 과 빈 본문**이 돌아옵니다.

### 1.1 추론은 예외가 아니라 모든 요청의 기본 비용입니다

`max_tokens=6000` 을 주고 질문 종류별 자연 추론 길이를 측정한 값입니다 (원본 §5.1).

| 질문 | n | 추론 토큰 p50 (범위) | 총 출력 p50 | 추론 비중 p50 | 지연 p50 | `finish_reason` |
|---|---|---|---|---|---|---|
| `1+1은? 숫자만 답하라` | 6 | 78 (49~81) | 82 | **95.1 %** | 1.94초 | 6/6 `stop` |
| 산수 서술형(사과 문제) | 6 | 139 (105~172) | 236 | 63.1 % | 5.32초 | 6/6 `stop` |
| 리그전 승점 추론 | 1 | 6,000 (한도 전량) | 6,000 | 100 % | **130.3초** | `length` |

`1+1은?` 의 실제 본문은 `2` 한 글자였고 출력 82토큰 중 78토큰이 추론이었습니다. **가장 사소한 질문조차 출력 예산의 95 %가 추론에 쓰입니다** — 따라서 `max_tokens` 를 "원하는 답변 길이" 로 잡으면 답을 받지 못합니다.

### 1.2 추론 폭주 — 예산을 키우면 실패까지 걸리는 시간만 늘어납니다

같은 질문(리그전 승점 추론)에 예산만 바꿔 반복한 결과입니다 (원본 §5.2).

| `max_tokens` | n | 추론 토큰 | 본문 길이 | `finish_reason` | 지연 | 본문 0자 |
|---|---|---|---|---|---|---|
| 800 | 2 | 800, 800 | 0, 0자 | length, length | 17.5, 17.4초 | **2/2** |
| 2,000 | 2 | 2,000, 2,000 | 0, 0자 | length, length | 43.3, 43.5초 | **2/2** |
| 4,000 | 2 | 3,570, 4,000 | 747, 0자 | length, length | 86.8, 86.9초 | 1/2 |
| 6,000 | 1 | 6,000 | 0자 | length | **130.3초** | 1/1 |

**7건 중 6건이 본문 0자**입니다. `max_tokens=4000` 의 두 건은 같은 질문인데 한 번은 추론이 3,570토큰에서 끝나 본문 747자를 냈고 다른 한 번은 4,000토큰을 전부 소비했습니다 — **추론 길이는 질문이 고정돼도 실행마다 크게 변동합니다.**

지연은 예산에 거의 정확히 선형입니다(출력 생성 속도 실측 45.62~46.15 tok/s, n=8). 즉 **예산 증액은 답을 받을 확률을 올리는 것이 아니라 실패를 늦게 알게 만드는 조치**입니다 — 800토큰이면 17초 만에 실패를 알고, 6,000토큰이면 130초를 태운 뒤 같은 실패를 받습니다.

### 1.3 어느 질문이 폭주할지 사전에 알 수 없습니다

주관적 난이도 순서를 따르지 않았습니다 (원본 §5.3). 열거 과제(1~60 중 조건 만족 정수 찾기)는 `max_tokens=2000` 에서 **2/2 정상 완료**(`finish_reason=stop`, 추론 952·1,214토큰, 본문 404·263자, 27.0·30.5초)였고, 같은 예산에서 리그전 승점 추론은 **2/2 실패**했습니다. **난이도 라벨이 아니라 과제 종류가 추론 길이를 결정합니다.**

사전 시험 설계에도 주의하십시오 — 추론이 짧은 질문만으로 예산 계단 시험(200 → 2,400, 각 5회)을 하면 **모든 단계에서 빈 본문 0건**이 나와 "어떤 예산이든 안전하다" 는 잘못된 결론에 도달합니다 (원본 §5.4).

### 1.4 오류가 아니라 HTTP 200 과 빈 본문이 돌아옵니다 — 왜 위험한가

```
HTTP 200 · finish_reason = "length"
completion_tokens = 6000  ← 전량 추론 · content = ""  ← 또는 None
```

- **HTTP 계층 재시도 · 회로차단기 · 모니터링이 전부 통과시킵니다.** 5xx 도 4xx 도 아니므로 오류율 대시보드에 0으로 잡힙니다. 그러면서 **요금과 GPU 시간은 전액 청구됩니다** — 130.3초 동안 A100 을 점유하고 6,000토큰을 생성한 결과가 빈 문자열입니다.
- **하류 파싱 코드가 빈 문자열을 "빈 답" 으로 사용자에게 그대로 전달합니다.** 실측의 4K 문서 요약 5건 중 **2건이 `finish_reason=length`** 였습니다(1건은 본문 0자, 1건은 문장 중간 절단). 특이한 질문이 아니라 평범한 요약 작업에서 나온 비율입니다.

### 1.5 유일하게 신뢰할 수 있는 감지 조건

**`finish_reason == "length"` 하나입니다** (원본 §5.5). 본문 유무와 무관합니다. 여기에 부가 조건을 붙이면 최악 사례를 놓칩니다.

- `and max_tokens < 2000` → **최악 사례가 `max_tokens=6000`(130.3초)이었으므로 정확히 그 건을 놓칩니다.**
- `and content == ""` → 절단을 놓칩니다. 산수 서술형 `max_tokens=300` 5건 중 1건이 본문 149자를 남기고 `...그중 4` 에서 끊겼습니다 (원본 §5.4).
- `and 질문유형 in (...)` → §1.3 대로 질문 유형으로는 예측할 수 없습니다.

`finish_reason` 은 단일 값이므로 정상 케이스와 겹치지 않습니다 — **조건을 더할 이유가 없습니다.**

### 1.6 `tool_calls` 가 있는 빈 본문은 정상입니다

도구가 필요한 추론 질문 5건 전부에서 추론(추론 토큰 p50 183)과 `tool_calls`(각 2개)가 함께 왔고 `content` 는 5/5 모두 비어 있었으며(원시 레코드에서는 `None`) `finish_reason` 은 `tool_calls` 였습니다 (원본 §6.4). OpenAI 규약상 정상입니다 — 도구를 호출하는 턴에는 본문이 없습니다. **구분은 `finish_reason` 값 하나로 끝납니다**: `tool_calls` = 정상, `length` = 실패.

### 1.7 구현 코드

```python
class IncompleteAnswer(Exception):
    """finish_reason == 'length' — 답이 없거나 문장 중간에서 절단됨."""


def read_response(resp):
    """응답을 검사해 (본문, 도구호출) 을 돌려준다."""
    choice = resp.choices[0]
    if choice.finish_reason == "length":         # ① 유일한 실패 신호. 부가 조건 없음
        raise IncompleteAnswer(
            f"불완전 응답: 출력 {resp.usage.completion_tokens}토큰, "
            f"본문 {len(choice.message.content or '')}자")
    if choice.finish_reason == "tool_calls":     # ② 빈 본문이 정상인 턴
        return None, choice.message.tool_calls
    return (choice.message.content or ""), None  # ③ content 는 None 일 수 있다


def ask_with_fallback(client, messages, tools=None):
    # 재시도에서 max_tokens 를 올리지 않는다. 추론 부담을 낮춘 프롬프트로 바꾼다.
    # simplify() = 질문 분할 · 중간 계산 결과 제공 · "간결히 답하라" 지시 추가 등
    for msgs in (messages, simplify(messages)):
        try:
            return read_response(_call(client, msgs, tools, max_tokens=1500))
        except IncompleteAnswer as err:
            last = err
    raise UserFacingFailure(
        "모델이 내부 추론에 응답 예산을 모두 소모해 답을 완성하지 못했습니다. "
        "질문을 더 작은 단계로 나눠 다시 시도해 주세요.", detail=str(last)) from last
```

사용자에게 알릴 내용은 **"오류가 발생했습니다" 가 아니라 "질문을 쪼개라" 여야 합니다.** 같은 질문을 그대로 재시도하면 §1.2 대로 같은 실패를 더 오래 기다린 뒤 받습니다. 타임아웃은 실측 46 tok/s 기준 `max_tokens / 46` 초 이상으로 잡으십시오 — 예산 4,000이면 최소 87초, 6,000이면 130초이며 여기에 프리필과 게이트웨이 비용을 더합니다(§2.4).

### 1.8 예산이 너무 작으면 전부 빈 본문이 됩니다 — 경계 실측

같은 산수 질문에 `max_tokens` 만 바꿔 각 6회 발사한 결과입니다(원시 `reliability.jsonl` · `R2_silent_empty`, 재계산).

| `max_tokens` | n | 본문 0자 | `finish_reason=length` | 추론 토큰 범위 | 지연 |
|---|---|---|---|---|---|
| 100 | 6 | **6/6** | 6/6 | 100 (전량) | 2.33~2.35초 |
| 200 | 6 | **4/6** | 5/6 | 127~200 | 4.49~4.52초 |
| 300 | 6 | **0/6** | 1/6 | 107~204 | 5.99~6.68초 |

이 질문의 추론은 실제로 107~204토큰을 필요로 합니다. 예산 100은 추론조차 마치지 못하는 크기라 **6/6 전부 빈 본문**이 되고, 300에서는 추론이 끝나 본문까지 나오므로 **빈 본문이 0건**이 됩니다. 세 가지를 함께 읽으십시오.

- **예산 부족은 조용한 실패로 나타납니다.** 100 → 6/6 전부 HTTP 200 이었습니다. "짧게 답하게 하려고 `max_tokens` 를 작게 잡는" 최적화가 **응답을 전멸시킬 수 있습니다.**
- **그렇다고 예산 증액이 해법은 아닙니다.** §1.2 의 폭주 질문은 6,000에서도 실패했습니다. 예산에는 **하한(추론이 끝나는 크기)과 무의미 구간(폭주 질문에서는 어떤 값도 안 됨)이 동시에 존재**하며 어느 쪽이든 감지 신호는 `finish_reason == "length"` 하나입니다.
- 300에서도 `finish_reason=length` 가 1/6 남았습니다(본문 161자, 절단) — **빈 본문이 0이 된다고 실패가 0이 되지는 않습니다.**

→ 질문 유형별 추론 토큰 실측치를 확보해 **그 상한의 2배 이상**을 예산으로 주되, 그것으로 §1.5 의 감지 코드를 대체하지 마십시오.

## 2. 체감 지연 — TTFT 를 SLA 로 쓰면 안 됩니다

### 2.1 사용자가 실제로 기다리는 시각은 TTFT 가 아닙니다

스트리밍 SSE 를 직접 파싱해 세 시점을 분리한 값입니다 (원본 §4.1).

| 조건 | n | TTFT p50 / p95 | 본문 첫 글자(TTFCT) p50 / p95 | 총 지연 p50 / p95 |
|---|---|---|---|---|
| 짧은 질문 (프롬프트 123 tok) | 8 | 0.271 / 0.544초 | **3.549 / 7.145초** | 6.322 / 10.875초 |
| 4K 문서 요약 (프롬프트 4,242 tok) | 5 (TTFCT 는 **4**) | 1.693 / 1.855초 | **15.622 / 32.958초** | 34.147 / 34.299초 |

첫 추론 델타 도착 시각은 8건 모두 TTFT 와 소수점까지 같았습니다 — **스트림의 첫 토큰은 항상 추론입니다.** 추론 단계가 총 지연에서 차지하는 몫은 짧은 질문 p50 55.2 %, 4K 요약 p50 77.4 % 였습니다. "첫 토큰이 0.27초에 온다" 는 사실이지만 **사용자 체감과 무관합니다.** SLA · 알림 임계값 · 타임아웃은 TTFCT 또는 총 지연으로 잡아야 합니다.

### 2.2 일단 본문이 시작되면 표시는 매끄럽습니다

| 조건 | 샘플 수 | ITL p50 | p95 | p99 | 최대 |
|---|---|---|---|---|---|
| 짧은 질문 | 2,299 | **21.4 ms** | 32.3 ms | 47.2 ms | 92 ms |
| 4K 문서 요약 | 5,762 | 21.6 ms | 35.3 ms | 59.4 ms | 160 ms |

> TTFCT 의 표본이 4 인 이유: 5건 중 1건이 `finish_reason=length` 로 본문 델타가 없어 본문 첫 글자 시각이 존재하지 않습니다.

프롬프트를 **34배로 늘려도 ITL p50 은 사실상 변하지 않았습니다**(21.4 → 21.6 ms, 원본 §4.2). 초당 약 46토큰이며 사람이 읽는 속도보다 빠릅니다. 고정 출력 조건(200·800·2,000·4,000토큰)에서 별도 측정한 생성 속도는 **45.62~46.15 tok/s**(n=8, p50 45.86)로 매우 좁게 모였습니다 — 타임아웃 산정에 그대로 쓸 수 있습니다. **이 배포의 지연 문제는 "느리게 흘러나오는 것" 이 아니라 "첫 글자가 늦는 것" 하나입니다.**

### 2.3 UI 설계 지침 (위 수치에서 직접 도출)

- **스트리밍을 켜십시오** — 게이트웨이가 SSE 를 버퍼링하지 않습니다(chunk 수 ≈ `completion_tokens`(게이트웨이 경유는 1~3토큰 차이가 정상 · 6건 중 4건 정확히 일치), 원본 §4.3). 단 **첫 chunk 를 본문으로 착각하지 마십시오.** 0.271초에 도착하는 첫 델타는 추론이며, 이를 본문 영역에 그리면 사용자가 모델의 사고 과정을 답으로 오해합니다 — `reasoning` 과 `content` 를 **분리해 렌더링**하십시오.
- **추론 구간은 접힌 "생각 중" 영역으로 표시하십시오.** 아무 표시도 없으면 사용자는 짧은 질문에서 **3.5초(p95 7.1초)** 동안 빈 화면을 봅니다. 임계값은 본문 첫 글자 p50 3.549초 · p95 7.145초에서 도출합니다 — **약 1초**부터 "생각 중" 을, **약 8초**(짧은 질문 p95 초과)부터 취소 버튼이나 남은 시간 안내를 노출하십시오. 프롬프트가 4K 급이면 본문까지 **p50 15.6초 · p95 33.0초**이므로 이 구간에서 진행 표시는 필수입니다.
- **취소 경로를 반드시 만드십시오.** 폭주 요청은 130초를 씁니다(§1.2). 사용자가 새로고침해도 GPU 는 그 요청을 계속 처리합니다.

### 2.4 응답 길이 → 지연 추정식

프리필과 디코드를 분리해 계산합니다.

```
총 지연[초]  ≈  프롬프트 토큰[tok] ÷ 프리필 속도[tok/초]     ← 프리필
              + 출력 토큰[tok]     ÷ 46 [tok/초]             ← 디코드 (추론 + 본문 합계)
              + 0.05 [초]                                    ← 게이트웨이 경유 (p95 0.22초)

본문 첫 글자까지[초] ≈ 프롬프트 토큰[tok] ÷ 프리필 속도[tok/초]
                      + 추론 토큰[tok]    ÷ 46 [tok/초]
```

- **프리필 속도**는 컨텍스트 길이에 따라 1,802~2,547 tok/초로 단조 감소합니다. 길이별 실측값과 문서 크기 변환표는 [부록 B2](appendix/B2_long_context_rag.md) 를 쓰십시오. 보수적 계산에는 하한 **1,800 tok/초**를 넣습니다.
- **출력 토큰**에는 추론 토큰이 포함됩니다(§1) — 최악 상한을 계산할 때는 `max_tokens` 를 그대로 넣으십시오. **게이트웨이 비용**은 요청당 +0.05초(p95 +0.22초, n=12쌍)이며 출력 길이와 무관합니다(경로별 비교는 [P1](P1_direct_vs_gateway.md)).

**검증**: 짧은 질문(프롬프트 123 tok · 실측 TTFT p50 0.271초 · 추론 토큰 p50 148, n=8)에 넣으면 첫 글자까지 0.271 + 148 ÷ 46 = 0.27 + 3.22 = **약 3.5초**이고 실측 TTFCT p50 은 3.549초입니다. 타임아웃 값은 위 식에 여유 계수 1.5를 곱해 잡으십시오(여유 계수는 관례이며 측정값이 아닙니다).

## 3. 도구 호출 (tool calling)

### 3.1 기본 동작은 신뢰할 수 있습니다

| 항목 | 결과 | 지연 p50 |
|---|---|---|
| 단일 도구 (`tool_choice: auto`) | **10/10** 정확히 1회 호출 · 이름 정확 · 인자 스키마 준수 | 1.527초 |
| 병렬 다중 도구 | **8/8** 각 응답에 `tool_calls` 3개 · 인자 전부 파싱 | 3.758초 |
| 불필요한 도구 호출(거짓 긍정) | **0/10** — `2+2` 질문에 도구를 주었으나 호출하지 않고 직접 답 | 1.235초 |
| 한국어 시스템 프롬프트 + 도구 | **8/8** 호출 · 인자 정확 | 1.496초 |

(원본 §6.1) 인자 JSON 파싱 · 필수 필드 존재 · 타입까지 기계적으로 검사한 결과입니다. **한국어 시스템 프롬프트가 도구 호출 정확도를 떨어뜨리지 않았으므로 언어별 우회 로직은 불필요합니다.** 표본이 각 8·10건이므로 "차이 없음" 은 이 규모에서의 전수 관측입니다.

### 3.2 `tool_choice` 로 특정 함수를 강제하는 것은 조용히 무시됩니다

`tool_choice: {"type": "function", "function": {"name": "get_weather"}}` 를 준 5건 전부, `tool_choice: "required"` 를 준 5건 전부에서 도구가 호출되지 않았습니다 (원본 §6.2 · §6.5).

```
HTTP 200 · finish_reason = "stop" · tool_calls = None
content = "안녕하세요! 네, 잘 지내고 있습니다. 😊 …"
```

(원시 레코드 `A3_forced_tool` · `agent.jsonl` · seq 0 본문의 앞부분입니다.)

- **오류가 아닙니다.** 강제 요청이 무시되고 모델이 대화로 답합니다.
- **`auto` 처럼 동작합니다.** 도구를 부를 이유가 있는 질문에서는 강제해도 5/5 호출되지만 그 질문은 `auto` 에서도 3/3 호출됩니다 — 강제가 작동한 증거가 아닙니다.
- **`"none"` 은 정상 작동합니다** — 호출 이유가 있는 질문에서 0/3 으로 억제됐습니다.
- **게이트웨이 경유와 직접 경로가 동일합니다.** 원인은 vLLM · `qwen3_xml` 파서 계층이며 **경로 우회로 해결되지 않습니다**(조건별 전체 결과 TC1~TC7, 각 n=3~5 는 [P1](P1_direct_vs_gateway.md)).

**영향**: "반드시 이 함수를 호출해야 한다" 를 전제로 응답을 파싱하는 코드는 `tool_calls is None` 에서 예외를 맞습니다. 의도 라우팅 · 구조화 추출 패턴이 여기서 깨집니다.

### 3.3 그래서 어떻게 구현해야 하는가

**구조화 데이터 추출이 목적이라면 `response_format` 을 쓰십시오.** `response_format: {"type": "json_object"}` 는 영문 키 **10/10**(지연 p50 3.257초), 한국어 키 **8/8**(3.879초) — 합계 **18/18** 파싱 성공이며 키 집합 `{직업, 경력년수, 재직중}` 이 게이트웨이·인코딩 단계에서 손상되지 않았습니다 (원본 §6.3).

**특정 도구를 반드시 부르게 해야 한다면 프롬프트 유도와 검증 루프로 처리합니다.**

```python
def call_tool_required(client, messages, tools, tool_name, retries=2):
    """tool_choice 강제는 무시되므로 검증 루프로 대체한다."""
    for _ in range(retries + 1):
        resp = _call(client, messages, tools, tool_choice="auto", max_tokens=1500)
        _, calls = read_response(resp)      # §1.7 — length 검사를 먼저 통과시킨다
        for c in (calls or []):
            if c.function.name == tool_name:
                return c
        messages = messages + [
            {"role": "user", "content": f"반드시 {tool_name} 도구를 호출해 주세요."}]
    raise ToolNotCalled(tool_name)
```

`tool_choice: "none"` 은 작동하므로 **도구를 쓰지 못하게 막는 용도로는 그대로 신뢰할 수 있습니다.**

### 3.4 추론과 도구 호출은 동시에 동작하며 그때 본문이 비는 것은 정상입니다

§1.6 대로 감지 코드가 `finish_reason == "tool_calls"` 인 빈 본문을 §1 의 조용한 실패와 섞으면 **정상 도구 호출 턴을 전부 실패로 오판합니다.**

## 4. 멀티턴 agent 루프 — 컨텍스트 누적 비용

### 4.1 실측: 4턴 × 5세션 — 누적 비용의 정체는 프롬프트 재전송이 아닙니다

도구 호출 → `role: "tool"` 결과 주입 → 최종 답변까지 실제 왕복을 측정했습니다 (원본 §6.6). 출력 토큰과 구간별 추정은 같은 원시 레코드에서 재계산한 값입니다(원시 `agent.jsonl` · `A6_agent_loop`).

| 턴 | 프롬프트 p50 | 출력 p50 | 지연 p50 | 지연 p95 | 프리필 추정 (프롬프트÷2,400) | 디코드 추정 (출력÷45.86) |
|---|---|---|---|---|---|---|
| 0 | 403 | 103 | 2.484초 | 2.819초 | 0.168초 | 2.246초 |
| 1 | 502 | 135 | 3.195초 | 3.718초 | 0.209초 | 2.944초 |
| 2 | 584 | 164 | 3.940초 | **13.407초** | 0.243초 | 3.576초 |
| 3 | 706 | 168 | 4.001초 | 5.422초 | 0.294초 | 3.663초 |

n=5 세션입니다. 턴3/턴0 지연 비 p50 은 **1.611배**, 프롬프트 토큰은 403 → 706(1.752배)입니다. 턴2 의 p95 13.407초는 5건 중 1건의 이상치이며 원인은 규명하지 않았습니다. 지연 증가 1.611배는 **출력 토큰 증가 1.631배와 거의 정확히 일치**하고 프롬프트가 303토큰 늘어난 데서 오는 프리필 증가는 **0.126초에 불과**합니다. 즉 이 규모(수백 토큰)의 멀티턴 비용은 **대화 이력 재전송이 아니라 뒤 턴에서 답이 길어지는 데서 발생합니다.** 실무 의미: 수백 토큰 규모의 이력을 잘라내는 최적화는 효과가 거의 없습니다. 이력이 수만 토큰(문서 주입 · 긴 도구 결과)으로 커질 때부터 프리필이 지배하며 그 구간의 실측 곡선은 [부록 B2](appendix/B2_long_context_rag.md) §1 에 있습니다.

### 4.2 `cached_tokens` 는 항상 `None` 입니다

`cached_tokens` 필드를 가진 원시 레코드 **1,273건 전수가 `None`** 이었습니다(재계산). **응답만 봐서는 대화 이력 재전송이 prefix 캐시로 절약되는지 알 수 없습니다.** 확인 방법은 `/metrics` 뿐이며 절차는 [부록 B2](appendix/B2_long_context_rag.md) §4 에 있습니다.

### 4.3 누적 비용 계산식과 대응 전략

```
세션 총 프리필[초] ≈ Σ(턴 i 의 프롬프트 토큰[tok]) ÷ 프리필 속도[tok/초]
세션 총 디코드[초] ≈ Σ(턴 i 의 출력 토큰[tok])     ÷ 46 [tok/초]
턴 i 의 프롬프트 토큰[tok] ≈ 시스템·도구 정의 + 문서·컨텍스트 + Σ(0..i-1)(질문 + 답변 + 도구 결과)
```

마지막 항이 턴 수에 대해 누적하므로 **긴 세션의 프롬프트 토큰은 선형이 아니라 이차적으로 쌓입니다**(턴당 재전송량 × 턴 수). 대응은 세 가지입니다.

- **요약 압축** — k턴을 넘으면 앞부분을 요약으로 대체합니다. 요약 호출 자체가 §1 의 추론 비용을 내므로 **요약 호출도 `finish_reason` 검사를 거쳐야 합니다.**
- **창 자르기** — 최근 k턴만 유지합니다. §4.1 대로 수백 토큰 규모에서는 이득이 작으므로 컨텍스트가 수만 토큰인 경우에만 씁니다.
- **프롬프트 접두사 고정 — 가장 효과가 큽니다.** 시스템 프롬프트 · 도구 정의 · 주입 문서를 **항상 같은 순서로 프롬프트 앞쪽에 고정**하고 변하는 부분(질문 · 최근 턴)을 뒤에 붙입니다. 이 배치에서 prefix 캐시가 실제로 듣는다는 근거는 [부록 B2](appendix/B2_long_context_rag.md) §4 의 실측입니다 — 같은 문서에 질문만 바꿀 때 프리필이 14.62초에서 0.63~1.15초로 **12.7~23.2배** 빨라졌습니다(적중률 65.4 %). 반대로 요청마다 타임스탬프 · UUID · 세션 ID 를 프롬프트 앞쪽에 넣으면 **접두사가 매번 달라져 캐시가 전부 무효화됩니다.**

## 5. 입력 검증이 느슨합니다 — 조용히 넘어가는 오타

잘못된 요청 10조건을 발사한 결과 **8건은 HTTP 400 과 정확한 원인 메시지**로 거절됐습니다 (원시 `reliability.jsonl` · `R1_*` — 원본 리포트 본문에는 이 항목의 절이 없습니다). 원인 문자열은 최상위 `error_code: BAD_REQUEST` 아래 `external_model_error` 안에 들어 있습니다 — 예: `"temperature must be in [0, 2], got 9.5. (parameter=temperature, value=9.5)"`. **그런데 예외가 2건 있습니다.**

| 조건 | 결과 | 왜 위험한가 |
|---|---|---|
| 알 수 없는 필드 | **HTTP 200** — 조용히 무시 | `max_token` 같은 **파라미터 오타가 드러나지 않습니다.** 의도한 설정이 적용되지 않은 채 정상 응답이 옵니다 |
| 틀린 모델명 | **HTTP 200** — 게이트웨이가 덮어씀 | 응답의 `model` 필드에는 실제 서빙 모델명이 돌아옵니다. **모델을 잘못 지정해도 성공**하므로 잘못된 대상에 트래픽을 보내도 알 수 없습니다 |

따라서 **고객이 자체 요청 검증을 가져야 합니다.**

```python
# 이 캠페인에서 게이트웨이 통과가 확인된 파라미터입니다(→ 부록 B1 §6).
# ⚠️ 목록이 좁으면 정상 요청이 막힙니다 — 조직에서 쓰는 파라미터를 반드시 추가하십시오.
ALLOWED = {"model", "messages", "max_tokens", "temperature", "top_p",
           "stream", "stream_options", "tools", "tool_choice",
           "response_format", "stop", "seed", "min_tokens", "ignore_eos",
           "n", "top_k", "presence_penalty", "frequency_penalty", "logprobs"}

def validate_payload(p, expected_model):
    if set(p) - ALLOWED:              # 게이트웨이는 200 을 주므로 여기서 막는다
        raise ValueError(f"알 수 없는 필드: {sorted(set(p) - ALLOWED)}")
    if p.get("model") != expected_model:
        raise ValueError(f"모델명 불일치: {p.get('model')}")
```

응답 쪽도 확인하십시오 — `resp.model` 이 기대한 모델명인지 검사하면 잘못된 엔드포인트 연결을 배포 직후에 잡습니다.

## 6. 개발자 체크리스트

각 항목 뒤의 §는 근거 절입니다.

- [ ] `finish_reason == "length"` 를 **본문 유무와 무관하게** 실패로 처리한다 (§1.5)
- [ ] 그 판별식에 `max_tokens` 값 · 본문 길이 · 질문 유형 같은 **부가 조건을 넣지 않는다** (§1.5)
- [ ] `finish_reason == "tool_calls"` 인 빈 본문은 정상으로 분기한다 (§1.6, §3.4)
- [ ] `content` 가 `None` 일 수 있으므로 `or ""` 로 방어한다 (§1.7)
- [ ] **`max_tokens` 증액을 재시도 전략으로 쓰지 않는다.** 질문 분할 · 프롬프트 단순화 · 포기 경로를 만들고, 사용자에게는 "질문을 쪼개라" 를 알린다 (§1.2, §1.7)
- [ ] 질문 유형별 추론 토큰을 실측해 상한의 2배 이상을 예산으로 잡는다. 예산을 작게 잡는 최적화는 응답을 전멸시킬 수 있다 (§1.1, §1.8)
- [ ] 타임아웃을 `max_tokens / 46` 초 이상으로 잡는다 (§1.7, §2.4)
- [ ] SLA · 알림 · 타임아웃을 TTFT 가 아니라 **TTFCT 또는 총 지연**으로 정의한다 (§2.1)
- [ ] 스트리밍을 켜고 `reasoning` 과 `content` 를 분리해 렌더링한다 (§2.3)
- [ ] 약 1초부터 "생각 중" 표시, 약 8초부터 취소·진행 안내를 노출하고 취소 경로를 만든다. 폭주 요청은 130초를 쓴다 (§2.3)
- [ ] 지연 추정에 §2.4 계산식을 쓰고 프리필 속도는 [부록 B2](appendix/B2_long_context_rag.md) 값을 쓴다 (§2.4)
- [ ] `tool_choice` 는 `auto` 와 `none` 만 신뢰한다. 특정 함수 지정과 `"required"` 는 조용히 무시된다 (§3.2)
- [ ] 구조화 추출은 `response_format: {"type": "json_object"}` 로 한다 (§3.3)
- [ ] 특정 도구 호출을 보장해야 하면 프롬프트 유도 + 검증 루프를 구현하고, 결과는 이름 · 인자 JSON · 필수 필드까지 검증한다 (§3.1, §3.3)
- [ ] 시스템 프롬프트 · 도구 정의 · 주입 문서를 **항상 같은 순서로 프롬프트 앞쪽에 고정**한다 (§4.3)
- [ ] 프롬프트 앞쪽에 요청마다 바뀌는 값(UUID · 타임스탬프)을 넣지 않는다 (§4.3)
- [ ] 캐시 적중 확인을 `cached_tokens` 로 하지 않는다. 항상 `None` 이다 (§4.2)
- [ ] 컨텍스트 압축(요약 · 창 자르기)은 이력이 수만 토큰 규모가 된 뒤에 적용한다 (§4.1, §4.3)
- [ ] 요청 필드 화이트리스트를 클라이언트에 두고 응답의 `model` 필드를 검사한다. 알 수 없는 필드와 틀린 모델명은 모두 200 으로 통과된다 (§5)
