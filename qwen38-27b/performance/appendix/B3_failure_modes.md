# 부록 B3 — 실패 모드 카탈로그 (운영팀용)

**대상 독자**: 이 엔드포인트를 호출하는 애플리케이션을 운영·감시하는 팀  
**작성 근거**: 2026-09-09 캠페인의 실측 실패 관측 — 400 8건 · 429 268건 · 502 133건 · HTTP 200 인데 본문 0자인 사례 다수  
**핵심 전제**: **HTTP 상태 코드만으로는 이 배포의 가장 흔한 실패를 감지할 수 없습니다.** 가장 위험한 실패가 200 으로 옵니다.

## 1. HTTP 200 인데 본문이 비어 있음 (추론 폭주) — **가장 위험**

| 항목 | 내용 |
|---|---|
| **증상** | 정상 응답처럼 보이지만 `message.content` 가 **0자**입니다. `usage` 는 토큰을 정상 청구하고 지연도 정상보다 길어집니다. |
| **HTTP 상태** | **200 OK** — 오류 코드도, 오류 본문도 없습니다. |
| **실측 특성** | 같은 어려운 추론 질문 7건 중 **6건이 본문 0자**였고 전부 `finish_reason=length` 였습니다. `max_tokens=6000` 에서는 **130.3초를 소모하고 본문 0자**였습니다. 예산을 키워도 성공률이 오르지 않고 **실패까지 걸리는 시간만 길어집니다**(약 46 tok/s 로 선형). 같은 산수 질문에서 본문 0자 비율은 `max_tokens` 100 에서 **6/6** · 200 에서 4/6 · 300 에서 **0/6** 이었습니다 — 질문에 따라 예산 임계값이 존재하지만, 300 에서도 1건은 `finish_reason=length` 로 문장이 중간에서 끊겼습니다(본문 161자). |
| **감지 방법** | **`finish_reason == "length"` 가 이 배포에서 유일하게 신뢰할 수 있는 신호입니다.** 본문 유무와 무관하게 실패로 처리하십시오(본문이 있으면 문장 중간 절단, 없으면 답 자체가 없음 — 둘 다 사용 불가). ⚠️ **`finish_reason == "tool_calls"` 인 빈 본문은 정상입니다** — reasoning 과 tool call 이 함께 동작할 때 본문은 비고 `tool_calls` 에 값이 들어갑니다. 두 조건을 반드시 분리하십시오. |
| **클라이언트 대응** | **`max_tokens` 증액을 재시도 전략으로 쓰지 마십시오** — 실패 시간만 늘어납니다. 질문을 쪼개거나, 추론 부담이 낮은 프롬프트로 바꾸거나, 상위 로직에서 포기하는 경로를 두십시오. 타임아웃은 `max_tokens ÷ 46` 초 이상으로 잡습니다(예산 6,000 이면 130초). |

상세한 근거와 질문 유형별 추론 길이는 [../P2_agent_workload.md](../P2_agent_workload.md) 를 보십시오.

## 2. 429 — rate limit 초과

| 항목 | 내용 |
|---|---|
| **증상** | 호출이 즉시 거절됩니다. 트래픽 급증 구간에서 몰려 나타납니다. |
| **HTTP 상태** | **429** · `error_code: REQUEST_LIMIT_EXCEEDED` · 메시지에 `Queries-per-minute (QPM) rate limit exceeded for endpoint` |
| **실측 특성** | 기본 한도 120 calls/분 상태에서 **`max_tokens=1` 요청 400건을 한꺼번에 발사**(wall 5.25초 · 실효 발사율 4,572.9 요청/분)하니 **200 이 133건 · 429 가 267건**이었습니다. **한도가 120 인데 133건이 통과했으므로 정확히 끊기지 않습니다.** 429 지연은 p50 0.184초(범위 0.096~0.253초)로 즉시 거절입니다. **응답에 `Retry-After` 헤더가 없습니다**(`content-type`·`server`·`x-request-id`·`x-databricks-org-id` 만). 회복은 버스트 직후 **+0초 429 → +10초부터 200**(이후 90초까지 계속 200)이었습니다. |
| **감지 방법** | HTTP 429 카운터와 **429 비율**(429 ÷ 전체 요청)을 계측하십시오. 한도가 정확히 끊기지 않으므로 "요청 수 < 한도" 라는 자체 계산으로는 예측할 수 없습니다. |
| **클라이언트 대응** | `Retry-After` 가 없으므로 **자체 지수 백오프 + 지터**를 구현해야 합니다. 아래 예시를 쓰십시오. |

```python
import random, time, requests

def call_with_backoff(url, headers, payload, max_attempts=5, base=1.0, cap=30.0):
    """429 전용 백오프. 429 회복 실측(+10초)을 근거로 상한을 잡되 지터로 동시 재시도를 흩뿌린다."""
    for attempt in range(max_attempts):
        r = requests.post(url, headers=headers, json=payload, timeout=180)
        if r.status_code != 429:
            return r                                    # 200 이든 4xx/5xx 든 호출자가 판단
        if attempt == max_attempts - 1:
            r.raise_for_status()
        sleep_s = min(cap, base * (2 ** attempt))        # 1 → 2 → 4 → 8 …
        sleep_s = sleep_s * (0.5 + random.random())      # 지터: 0.5x ~ 1.5x
        time.sleep(sleep_s)
    raise RuntimeError("unreachable")
```

> ⚠️ **위 10초는 429 회복만의 관측값입니다.** 다른 실패 모드(502 등)의 백오프 값으로 옮겨 쓰면 안 됩니다. 502 의 복구 시간은 상류 vLLM 재기동 시간에 달려 있고 **10초와 자리수가 다릅니다**(§5·§8). 실패 모드별로 백오프 정책을 분리하십시오.

한도를 올리는 방법과 GPU 포화와의 관계는 [../P3_capacity_and_cost.md](../P3_capacity_and_cost.md) §6 에 있습니다.

## 3. 400 BAD_REQUEST — 컨텍스트 초과

| 항목 | 내용 |
|---|---|
| **증상** | 긴 프롬프트를 보내면 생성이 시작되지 않고 즉시 거절됩니다. |
| **HTTP 상태** | **400** · `error_code: BAD_REQUEST` · 원인은 `external_model_error` 안에 정확히 들어 있습니다. |
| **실측 특성** | **`프롬프트 토큰 + max_tokens > 131,072`** 이면 거절됩니다. 즉 `max_tokens` 가 컨텍스트 예산에 포함됩니다. 240,447자 프롬프트 + `max_tokens` 1,500 → 400(0.43초) · 288,537자 → 400(0.45초). 거절은 **0.38~0.45초(n=4)에 즉시**이므로 GPU 시간을 낭비하지 않습니다. ⚠️ 오류 메시지의 `at least 129573 input tokens` 는 **실측 토큰 수가 아니라 `131072 − max_tokens + 1` 인 거절 하한**입니다(프롬프트 크기가 1.2배 달라도 같은 값). 성공한 최대 프롬프트는 104,536 토큰이었고 **그 위 경계는 측정하지 않았습니다.** |
| **감지 방법** | 400 응답 본문의 `external_model_error` 를 파싱하십시오. 상한 메시지가 `This model's maximum context length is 131072 tokens...` 형태로 정확히 옵니다. |
| **클라이언트 대응** | **사전 계산으로 피할 수 있는 실패입니다.** 요청 전에 `프롬프트 토큰 ≤ 131,072 − max_tokens` 를 검사하십시오. 한국어는 장문 구간 실측 **0.543 tok/자**이므로 `max_tokens=1500` 이면 프롬프트 상한은 129,572 토큰 ≈ **약 238,000자**입니다(밀도가 0.544 면 더 줄어들므로 **표값의 99 % 이하**로 잡으십시오). 초과 시 문서를 잘라 보내거나 `max_tokens` 를 줄입니다. |

## 4. 400 — 잘못된 요청 · 그리고 **조용히 넘어가는 예외 2건**

| 항목 | 내용 |
|---|---|
| **증상** | 잘못된 파라미터는 대부분 400 으로 정확히 거절됩니다. **그러나 일부는 오류 없이 200 이 됩니다.** |
| **HTTP 상태** | **400** (`error_code: BAD_REQUEST`) — 10조건 중 **8건**. 나머지 2건은 **200**. |
| **실측 특성** | 400 으로 정확히 거절된 8건: 빈 `messages` · 음수 `max_tokens` · 0 `max_tokens` · 잘못된 `role` · `tools` 에 없는 `tool_choice` · 잘못된 `response_format` · 범위 밖 `temperature`(0~2) · 빈 `tools` 배열. 메시지가 `external_model_error` 안에 파라미터명·값까지 정확히 들어 있습니다(예: `temperature must be in [0, 2], got 9.5`). **예외 2건**: ① **알 수 없는 필드 → 200**(조용히 무시) ② **틀린 모델명 → 200**(게이트웨이가 `external_model.name` 으로 덮어씀). |
| **감지 방법** | 400 은 최상위 `error_code` 가 원인과 일치하므로 쉽게 처리됩니다. **예외 2건은 런타임에 감지할 수 없습니다** — 오타가 오류로 드러나지 않고 그대로 성공합니다. |
| **클라이언트 대응** | 파라미터 이름과 모델명을 **배포 시점에 검증**하십시오(스키마 검증 · 상수화 · 코드 리뷰). 런타임 응답으로는 잡히지 않습니다. `model` 필드는 게이트웨이가 덮어쓰므로 클라이언트 값이 틀려도 무해하지만, 그 때문에 **엔드포인트를 잘못 지정한 실수도 성공처럼 보입니다.** |

## 5. 502 — 상류(vLLM) 사망

| 항목 | 내용 |
|---|---|
| **증상** | 모든 호출이 502 로 떨어집니다. 게이트웨이는 살아 있고 vLLM 프로세스만 없는 상태입니다. |
| **HTTP 상태** | **502** · 최상위 `error_code` 는 **`INTERNAL_ERROR` 로 원인과 어긋납니다.** 진짜 원인은 `external_model_error` 안의 `<html><title>502 Bad Gateway</title>...nginx` 입니다. 400 계열과 달리 최상위 코드를 믿을 수 없습니다. |
| **실측 특성** | 측정 중 상류가 재기동되어 **502 를 133건** 관측했습니다. 그중 **132건은 프롬프트 크기와 무관하게 0.037 ~ 0.314초에 즉시** 떨어졌습니다(프롬프트 52자든 288,537자든 동일). **이미 생성 중이던 1건만 28.47초를 기다린 뒤** 502 가 되었습니다. |
| **감지 방법** | 502 카운터와 함께 **502 의 지연 분포**를 계측하십시오. 0.3초 이내 502 와 수십 초 뒤 502 는 성격이 다릅니다. |
| **클라이언트 대응** | 아래 「빠른 실패와 느린 실패」 를 반영하십시오. |

**빠른 실패와 느린 실패는 타임아웃 설계에서 다르게 다뤄야 합니다.**

- **0.3초 이내 502(132/133)** — 상류가 아예 없는 상태입니다. **재시도 대기가 아니라 명확한 실패**이며, 시간을 거의 잃지 않았으므로 **즉시 재시도할 가치가 있습니다.** 클라이언트 타임아웃과 무관하게 도착하므로 타임아웃을 짧게 잡아도 손해가 없습니다.
- **28.47초 뒤 502(1/133)** — 이미 생성이 진행 중이던 요청이 서버 사망으로 끊긴 경우입니다. **이 요청은 이미 시간을 잃었습니다.** 사용자 대기 시간 예산을 다 쓴 뒤이므로 즉시 재시도는 사용자 체감을 두 배로 나쁘게 만듭니다. 여기서는 **재시도보다 사용자에게 실패를 알리는 것**이 낫습니다.
- 따라서 **502 의 재시도 판단을 지연으로 분기**하십시오 — 빠른 502 는 즉시 1~2회 재시도, 느린 502 는 즉시 실패 반환. **§2 의 10초 백오프를 여기에 옮겨 쓰지 마십시오.** 502 의 복구는 상류 재기동 시간(§8)에 달려 있습니다.

## 6. 엔드포인트가 `READY` 인데 호출이 실패합니다

| 항목 | 내용 |
|---|---|
| **증상** | 서빙 엔드포인트 상태 조회는 `READY` 인데 실제 호출은 전부 502 입니다. |
| **HTTP 상태** | 상태 조회 **200 · `READY`** / 실제 호출 **502** |
| **실측 특성** | 상류 vLLM 이 죽어 있던 45초 동안 **엔드포인트 상태는 계속 `READY`** 였고 그 사이 요청 133건이 전부 502 였습니다. 상태 필드는 게이트웨이 계층의 구성 상태이며 **상류 vLLM 프로세스의 생존을 보장하지 않습니다.** |
| **감지 방법** | **상태가 아니라 실제 호출로 판정하십시오.** 두 가지를 함께 봅니다 — ① driver-proxy `/health` 가 200 ② 게이트웨이 `invocations` 가 실제 요청에 200. 실측 헬스체크에서 `/health` 200 · 작은 `invocations` 200(2.86초)을 확인했습니다. |
| **클라이언트 대응** | 아래 구현 지침을 따르십시오. |

**헬스체크 구현 지침**

- **`/health` 는 본문이 0바이트입니다.** 본문 문자열로 판정하면 **절대 통과하지 않습니다.** HTTP 상태 코드만 보십시오.
- **`/health` 200 만으로는 부족합니다.** driver-proxy 는 살아 있어도 vLLM 이 죽었을 수 있고, 반대로 게이트웨이 구성 오류로 `invocations` 만 실패할 수도 있습니다. **둘을 모두 요구**하는 AND 조건으로 만드십시오.
- **`invocations` 헬스체크는 최소 요청으로** 보냅니다(`max_tokens` 을 작게). 실측에서 작은 호출도 **2.86초**가 걸렸으므로 헬스체크 타임아웃을 1초 같은 값으로 잡으면 정상 상태를 실패로 오판합니다.
- 배치 작업·장시간 작업의 **진입부에 이 가드를 두십시오.** 상태만 보는 가드는 사고를 놓칩니다.

## 7. 클러스터 자동 종료가 엔드포인트를 죽입니다

| 항목 | 내용 |
|---|---|
| **증상** | 한동안 잘 쓰던 엔드포인트가 어느 시점부터 전부 502 입니다. 엔드포인트 상태는 `READY` 입니다. |
| **HTTP 상태** | **502** (§5 와 응답 표면이 같습니다) |
| **실측 특성** | vLLM 은 클러스터 드라이버 프로세스에서 돌기 때문에 **클러스터가 종료되면 엔드포인트도 함께 죽습니다.** 검증 환경에서 `INACTIVITY · 90분` 종료가 관측되었습니다. ⚠️ **추론 트래픽만으로 자동 종료 타이머가 갱신되는지는 직접 측정되지 않았습니다** — 관측 구간에는 게이트웨이 트래픽이 아예 없어 구분이 불가능했습니다. 갱신되지 않는다고 **가정하고** 설계하십시오. |
| **감지 방법** | 502 가 다발하면 **엔드포인트 상태가 아니라 클러스터 상태**를 확인하십시오. 종료 사유(`INACTIVITY`)가 클러스터 이벤트에 남습니다. |
| **클라이언트 대응** | 예방이 유일한 대응입니다 — **`autotermination_minutes: 0`** 을 **클러스터 생성 시점에** 지정하십시오(실행 중 변경은 재시작을 유발해 `/local_disk0` 캐시를 날립니다). 그 대신 **과금이 계속되므로 반드시 수동으로 종료**하는 운영 절차를 함께 두십시오. → [../../deployment/STEP2_cluster_and_runtime.md](../../deployment/STEP2_cluster_and_runtime.md) · [../../deployment/STEP4_ai_gateway.md](../../deployment/STEP4_ai_gateway.md) |

## 8. 재기동 다운타임 — 운영 중 재기동 시 예상 정지 시간

| 조건 | 실측 | 계획에 쓸 값 |
|---|---|---|
| 재기동 (torch.compile 캐시가 `/local_disk0` 에 남아 있음) | **45초 · 190초** (각 1회 관측) | **190초** |
| 콜드 기동 (캐시 없음) | **280 ~ 319초** (131K 프로필 관측 280초 · 319초) · 262K 프로필 약 320초 | **320초** |

⚠️ **캐시가 있는 재기동에서 45초와 190초가 같은 조건 라벨로 관측되었고 차이의 원인은 규명되지 않았습니다.**
따라서 다운타임 계획은 **보수값(190초)** 으로 세우십시오. 45초를 SLA 근거로 쓰면 안 됩니다.

**그 사이에 어떤 일이 벌어지는가** — 실측된 45초 정지 구간에서 요청 **133건이 전부 502** 였고
엔드포인트 상태는 계속 `READY` 였습니다(§5·§6). 즉 **재기동 다운타임은 "느린 응답" 이 아니라
"전량 502"** 로 나타납니다.

**운영 대응**  
· 재기동은 **트래픽이 없는 시간대**에 계획하고, 다운타임을 위 보수값으로 사전 공지하십시오.  
· 무중단이 필요하면 GPU 를 2장 이상 두고 순차 재기동해야 합니다. **다중화 구성은 이 캠페인에서 측정되지 않았습니다** → [../P3_capacity_and_cost.md](../P3_capacity_and_cost.md) §7  
· 재기동 후에는 **§6 의 헬스체크(둘 다 200)** 로 복구를 확인한 뒤 트래픽을 되돌리십시오. 상태 필드만 보면 복구 전에 트래픽이 들어갑니다.

## 9. 운영 대시보드 최소 지표

아래 5개를 계측하면 위 실패 모드를 **사용자 신고 전에** 볼 수 있습니다.

| 지표 | 어디서 | 무엇이 보이는가 | 경보 기준(제안 · 관례) |
|---|---|---|---|
| **`finish_reason` 분포** | 애플리케이션 로그 | `length` 비율이 곧 **추론 폭주 비율**입니다. 이 배포에서 200 응답의 실패를 볼 수 있는 유일한 지표입니다. `tool_calls` 는 분리해 세십시오 | `length` 비율이 평시 기준선 대비 상승 |
| **429 비율** | 애플리케이션 로그 (HTTP 상태) | 한도 접근·초과. 한도가 정확히 끊기지 않으므로 요청 수 계산으로는 대체 불가 | 0 보다 크면 조사 · 지속되면 한도 상향 검토 |
| **502 비율 + 502 지연 분포** | 애플리케이션 로그 | 상류 사망·자동 종료·재기동. **0.3초 이내 502 와 수십 초 502 를 나눠** 기록하십시오(§5) | 0 보다 크면 즉시 조사 |
| **TTFCT** (본문 첫 글자까지) | 애플리케이션 계측 (스트리밍) | 사용자 체감 지연. 첫 SSE chunk(TTFT)는 추론의 시작이므로 **SLA 지표로 쓰면 안 됩니다** | 평시 p95 대비 상승 |
| **`/metrics` 의 `running` · `waiting` · `kv_cache_usage_perc`** | driver-proxy `.../8005/metrics` | GPU 포화 여부와 병목 종류. `running` 이 `--max-num-seqs` 에 붙고 `waiting` 이 쌓이면 용량 부족입니다 | `waiting` 이 지속적으로 0 보다 큼 |

**함께 두면 좋은 것**  
· `usage.completion_tokens` 와 `usage.completion_tokens_details.reasoning_tokens` 를 함께 기록하십시오. 추론 비중이 곧 **비용의 대부분**이며 유형별 `max_tokens` 를 정하는 근거가 됩니다.  
· `cached_tokens` 는 **항상 `None`** 이므로 prefix 캐시 적중을 애플리케이션 로그로는 알 수 없습니다. `/metrics` 의 `vllm:prefix_cache_hits_total` 로만 확인됩니다 → [B2_long_context_rag.md](B2_long_context_rag.md)  
· 경보 기준값은 **이 캠페인에서 측정된 값이 아니라 운영 관례**입니다. 배포 후 2주 정도의 기준선을 쌓아 조정하십시오.
